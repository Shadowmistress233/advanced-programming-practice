# 一、概述

## （一）编写目的

本文档在《03-01 需求开发概要设计说明书（V1.1）》冻结后编写，将系统总体方案细化到可直接编码的类清单、方法签名、处理流程、并发与幂等规则、异常分支、建表语句与核心时序。概要设计定义“有哪些模块与对外契约”，本文档定义“每个类与方法怎么写”，两者交叉引用、不重复定义接口字段。

## （二）适用范围

适用于本平台全部 15 个业务模块及 7 项公共组件的编码、联调、代码评审与测试设计。文中约定的包名、类名、方法名、DTO/VO 与字段名即为编码契约；编码期确需调整时须同步更新本文档并通知测试负责人。

## （三）术语与缩略语

| 术语 | 说明 |
| --- | --- |
| DTO | Data Transfer Object，接口入参对象，承载请求字段与校验注解 |
| VO | View Object，接口出参对象，按页面展示裁剪字段，禁止直接返回实体或密码字段 |
| 状态机 | 将状态枚举与合法状态迁移集中收口到枚举或领域服务，禁止在业务代码中散落判断 |
| 条件更新 | 通过 `UPDATE ... WHERE id = ? AND status = ?` 结合影响行数判断并发抢占是否成功 |
| 幂等 | 同一请求或定时任务重复执行时结果一致，不产生重复单据、重复扣分或重复消息 |
| 降级 | Redis、PDF 生成等非核心依赖不可用时捕获异常并切至备用实现，保证主流程可用 |

# 二、总体设计

## （一）包结构与分层

后端源码统一置于 `com.csu.campusloop` 根包下，严格单向分层，禁止下层反向调用上层：

| 子包 | 职责内容 | 编码约束 |
| --- | --- | --- |
| `controller` | 15 个业务模块的页面与 API 控制器 | 仅做 `@Valid` 参数校验、获取会话 `LoginUser`、调用 Service 并封装 `Result<T>` |
| `service` / `service.impl` | 业务接口与实现类（含 `FileStorageService`） | 事务边界与状态流转收口于此层；禁止在 impl 内调用 Controller |
| `mapper` | MyBatis Mapper 接口（对应 `resources/mapper/*.xml`） | 仅做持久化访问；参数一律使用 `#{}` 占位，禁止在 Service 拼 SQL |
| `entity` | 与 15 张表一一对应的持久化实体 | 仅含属性与 getter/setter，不直接作为接口返回值暴露 |
| `dto` / `vo` | 入参 DTO（含 `PageQuery`）与出参 VO（含 `Result`、`PageResult`、`LoginUser`） | 按接口拆分，DTO 携带校验注解，VO 严格脱敏 |
| `enums` | 错误码与状态枚举 | 集中定义 `ErrorCode`、物品/流转单/捐赠/举报/活动状态机枚举 |
| `config` | 配置类与常量（含 `RedisKey`、会话常量与 Jackson `ObjectMapper` 配置） | 数据源、Redis、拦截器注册、路径/字典常量与 `JavaTimeModule` 统一日期序列化 |
| `interceptor` | SpringMVC 拦截器 | 登录会话校验、账号实时停用复核、白名单精确放行与同源 CSRF 防护 |
| `aspect` | AOP 切面与 `@OperLog` 注解 | `@OperLog` 操作审计异步落库与敏感字段脱敏切面 |
| `task` | 定时任务 | 流转单三段超时巡检、每日运营数据预聚合 |
| `util` | 公共工具类（含 `RedisHelper`、`PermissionUtil` 等） | BCrypt 密码、日期、单号、图片压缩、二维码、PDF、Excel、敏感词、权限与缓存降级 |
| `exception` | 异常与全局处理 | `BizException`、`GlobalExceptionHandler` |

## （二）请求处理链路

HTTP 请求依次经过：`CharacterEncodingFilter` → `AuthInterceptor` → `Controller` → `Service`（含 `@OperLog` 切面与 `@Transactional`）→ `Mapper` → `MySQL / Redis`，响应沿原路返回，未捕获异常由 `GlobalExceptionHandler` 兜底转换。

1、Filter 仅负责 UTF-8 编码，不编写业务逻辑。

2、`AuthInterceptor` 按 HTTP 方法与路径/正则精确判定白名单；对受保护请求校验 Session 中的 `LoginUser`，调用 `AuthService.getAuthState(userId)` 按主键实时复核 `user.status`、`auth_status` 与 `role`（若账号不存在或已被停用则立即销毁 Session 并按 Ajax/页面区分返回 `1005` 或跳转登录页），同时对写请求执行同源来源校验。

3、Controller 负责 `@Valid` 格式校验、从 Session 提取 `LoginUser` 与调用 Service，不编写 SQL 或复杂分支。

4、Service 负责权限归属校验、业务规则校验、状态条件更新、事务管理与 Redis/PDF 异常降级。

5、Mapper 仅执行参数化 SQL，返回实体或查询 VO。

## （三）公共约定

| 约定项 | 具体要求 |
| --- | --- |
| 主键与金额 | 所有表主键与接口业务 ID 统一 `Integer`；金额统一 `BigDecimal`（`RoundingMode.HALF_UP`，保留 2 位），禁止 `double`/`float` |
| 密码安全 | 统一经 `PasswordUtil` 使用 BCrypt 不可逆哈希存储与比对，禁止明文入库或日志输出 |
| 事务边界 | 涉及多表写操作、成对锁定/解锁、积分原子变更或活动报名扣减的 Service 方法一律标注 `@Transactional(rollbackFor = Exception.class)` |
| 并发与防重 | 禁止“先查后改”；锁单、核销、积分增减与活动名额扣减全部采用数据库原子更新或条件更新，校验影响行数等于 1 才算成功 |
| 异常处理 | 业务校验失败统一抛出 `BizException(ErrorCode)` 或 `BizException(ErrorCode, String customMsg)`，禁止吞掉异常静默返回 `null` |
| 缓存与降级 | Redis 键一律由 `RedisKey` 生成并强制带 TTL；所有 Redis 读写均经 `RedisHelper` 用 `try/catch` 包裹，失败返回降级值并记 `warn` 日志 |
| 分页与时间 | 使用 `PageHelper.startPage(page, pageSize)` 后紧跟单条查询（默认 `page=1, pageSize=12`，上限 `50`）；时间统一 `LocalDateTime`（`yyyy-MM-dd HH:mm:ss`，由全局 `ObjectMapper` 注册 `JavaTimeModule` 序列化） |

# 三、公共组件详细设计

## （一）统一返回与错误码

`Result<T>` 位于 `com.csu.campusloop.vo`，封装 `{code, msg, data}` 三字段，JSON 接口 HTTP 状态码固定返回 `200`，由 `code` 区分结果；错误码全部收口在 `com.csu.campusloop.enums.ErrorCode` 枚举中，与《03-01 需求开发概要设计说明书（V1.1）》第四章（二）逐条一致，严禁在业务代码中硬编码数字错误码。

二进制流接口例外约定：核销二维码下载（`#18 GET /api/orders/{id}/qrcode`，`image/png`）、电子捐赠凭证下载（`#22 GET /api/donations/{id}/certificate`，`application/pdf`）与运营报表导出（`#36 GET /api/admin/dashboard/export`，`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`）成功时直接向 `HttpServletResponse` 写出字节流。鉴权、归属校验与文件/数据存在性检查必须在设置下载响应头与获取 `OutputStream` 之前完成，校验失败时直接抛出 `BizException`，由 `GlobalExceptionHandler` 正常返回 `Result<Void>` JSON。

```java
package com.csu.campusloop.vo;

import com.csu.campusloop.enums.ErrorCode;

public class Result<T> {
    private Integer code; // 0 成功，其余见 ErrorCode
    private String msg;   // 中文提示
    private T data;       // 业务数据，可为 null

    public static <T> Result<T> ok(T data) { /* code=0, msg="ok" */ }
    public static Result<Void> ok() { /* code=0, msg="ok", data=null */ }
    public static <T> Result<T> fail(ErrorCode errorCode) { /* 取枚举 code 与 msg */ }
    public static <T> Result<T> fail(ErrorCode errorCode, String customMsg) { /* 保留枚举 code，覆写提示 */ }
    public static <T> Result<T> fail(Integer code, String msg) { /* 仅框架内部或兜底调用 */ }
}
```

## （二）全局异常处理

`BizException` 继承 `RuntimeException`，持有 `ErrorCode errorCode` 与可选覆盖文案 `customMsg`，提供 `BizException(ErrorCode)` 与 `BizException(ErrorCode, String customMsg)` 两个构造器。`GlobalExceptionHandler` 使用 `@RestControllerAdvice` 统一拦截控制层与业务层抛出的异常并转换为标准 `Result`：

| 异常类型 | 返回错误码 | 处理逻辑与日志级别 |
| --- | --- | --- |
| `BizException` | `e.getCode()` | 直接返回 `e.getMsg()`，记录 `warn` 日志 |
| `MethodArgumentNotValidException` / `BindException` / `ConstraintViolationException` | `1001` | 提取首条参数校验失败提示返回，记录 `warn` 日志 |
| `MissingServletRequestParameterException` / `MethodArgumentTypeMismatchException` / `HttpMessageNotReadableException` / `MissingServletRequestPartException` | `1001` | 返回“请求参数格式不正确或缺少必填项”，不暴露底层反序列化类名，记录 `warn` 日志 |
| `MaxUploadSizeExceededException` | `2001` | 返回“上传图片大小超限（单张不超过 2MB）”，记录 `warn` 日志 |
| `DuplicateKeyException` | `2301` / `2402` / `5001` | 模块 07（评价）与模块 15（活动报名）优先在业务层捕获并执行补偿（模块 15 回补 Redis 预筛名额）后再抛对应 `BizException`；全局处理器按 `e.getMostSpecificCause().getMessage()` 兜底映射：`uk_order_from`→`2301`、`uk_activity_user`→`2402`，其余唯一键冲突记录 `error` 日志返回 `5001` |
| `Exception` | `5001` | 记录完整堆栈 `error` 日志，对外统一返回“系统繁忙，请稍后重试”，严禁向前端透传堆栈或 SQL |

## （三）登录拦截与权限判定

会话对象统一定义为 `com.csu.campusloop.vo.LoginUser`，包含 `userId`（`Integer`）、`username`、`realName`、`role`、`campus`、`authStatus`（`Integer`）六个字段，在 `HttpSession` 中以常量 `AuthConstants.SESSION_LOGIN_USER` 键名存储。

1、白名单精确放行规则：`AuthInterceptor`（实现 `HandlerInterceptor`）严禁将 `/api/**` 公开接口直接配置到 SpringMVC 仅按 URI 匹配的 `excludePathPatterns`（防止与同 URI 的写接口 `POST /api/items`、`POST /api/skills`、`POST /api/reviews`、`POST /api/activities` 碰撞，或用通配符误放行 `GET /api/items/mine`）。`excludePathPatterns` 仅放行静态资源（`/static/**`、`/upload/**`，严禁放行 `/certificate/**`）；其余路径全部在 `preHandle` 中按“HTTP 方法 + 精确路径/纯数字正则”判定：
   公开页面路由（`GET`）：`/login`、`/`、`/index`、`/items`、`^/items/\d+$`、`/skills`、`/activities`、`/donations/verify`；
   公开 API 路由：`POST /api/auth/login`、`GET /api/items`、`GET ^/api/items/\d+$`、`GET /api/categories/tree`、`GET /api/recommendations`、`GET /api/skills`、`GET /api/reviews`、`GET /api/activities`、`GET ^/api/activities/\d+$`、`GET /api/donations/verify`。

2、公开/登录双态接口约定：`GET /api/recommendations`、`GET /api/items/{id}`、`GET /api/activities/{id}` 属于白名单公开读接口，未登录允许浏览；若请求携带有效 Session，Service 层可读取其中的 `LoginUser` 渲染个人态信息（如收藏态、本人物品管理入口与报名态），不额外触发未登录拦截。

3、受保护接口会话校验与实时停用拦截：未命中白名单的请求必须存在有效 `SESSION_LOGIN_USER`；未登录时 Ajax 请求（URI 以 `/api/` 开头或请求头含 `X-Requested-With: XMLHttpRequest`）写出 `Result.fail(ErrorCode.UNAUTHORIZED)` JSON，页面请求重定向至 `/login`。已登录时调用 `AuthService.getAuthState(loginUser.getUserId())` 按主键实时查询 `status`、`auth_status` 与 `role`：若记录不存在或 `!Integer.valueOf(1).equals(state.getStatus())`，立即调用 `session.invalidate()`，Ajax 请求写出 `Result.fail(ErrorCode.ACCOUNT_DISABLED)` JSON，页面请求重定向至 `/login?disabled=1`；账号正常时将最新的 `authStatus` 与 `role` 同步回写至 Session 中的 `LoginUser`，避免权限变更后持有旧态。

4、同源 CSRF 校验：对所有已通过登录校验的 `POST` 写接口，校验请求头 `Origin`（缺失时回退检查 `Referer`）是否与当前站点协议、主机及端口一致；存在跨站来源时立即拒绝并返回 `Result.fail(ErrorCode.FORBIDDEN)`。

5、细粒度权限校验统一收敛至 `com.csu.campusloop.util.PermissionUtil`，全部方法在校验不通过时统一抛出 `BizException(ErrorCode.FORBIDDEN)`：
   `checkRole(LoginUser user, String... roles)`：校验当前角色在允许列表内；
   `checkAuthenticatedStudent(LoginUser user)`：校验角色为 `student` 且 `Integer.valueOf(1).equals(user.getAuthStatus())`，用于全部校园业务写接口；
   `checkOwner(Integer currentUserId, Integer ownerId)`：校验当前用户为资源归属人；
   `checkOrderParticipant(LoginUser user, ExchangeOrder order)`：校验当前用户为流转单发起方或目标物品所有者；
   `checkOrderQrOwner(LoginUser user, ExchangeOrder order)`：仅允许物品所有者（`to_user_id`）获取核销二维码（`#18`）；
   `checkOrderVerifier(LoginUser user, ExchangeOrder order)`：仅允许流转单发起方（`from_user_id`）提交扫码/输码核销（`#17`）；
   `checkClubAccess(LoginUser user, Integer clubId)`：校验社团账号（`role="club"`）仅可读写归属本社团的数据，管理员按接口规则显式放行。

## （四）分页与查询封装

列表查询入参统一继承 `com.csu.campusloop.dto.PageQuery`（含 `page` 默认 `1`、`pageSize` 默认 `12`，服务端强制将 `page < 1` 修正为 `1`、`pageSize` 裁剪至 `[1, 50]`）。Service 层在单条列表查询前紧邻调用 `PageHelper.startPage(query.getPage(), query.getPageSize())`，统一经 `PageResult.of(List<T> list)` 封装为 `com.csu.campusloop.vo.PageResult<T>{total, list, pages, page, pageSize}` 返回。

说明：`PageResult<T>` 对外协议严格对齐《03-01 需求开发概要设计说明书（V1.1）》第四章（一）约定的 `PageInfo<T>{total, list, pages}` 核心三字段，并补充回显当前 `page` 与 `pageSize`，避免直接序列化 PageHelper 原生 `com.github.pagehelper.PageInfo` 暴露十余个无关内部字段。动态排序字段一律通过服务端 `Map<String, String>` 白名单映射为合法列名，禁止拼接前端传入字段名。

## （五）文件上传与目录隔离

`com.csu.campusloop.service.FileStorageService` 严格区分两类位于应用 WAR 包外部的本地目录，操作系统与 Tomcat 均禁用两目录的脚本执行权限：

1、物品实拍图目录（`upload/yyyyMM/`，允许 Tomcat 配置静态只读映射）：`saveItemImage(MultipartFile file)` 严格按“非空与大小校验（≤ 2MB）→ 扩展名白名单（`jpg`/`jpeg`/`png`/`webp`）→ 文件头魔数校验（不信任客户端 `Content-Type`）→ `ImageUtil` 解码重编码压缩（剥离 EXIF 与潜在脚本，主图最大宽 1200px，命名 `{uuid}.jpg`；同步生成宽 300px 缩略图，命名 `{uuid}_thumb.jpg`）”顺序执行，任意校验失败抛 `BizException(ErrorCode.IMAGE_INVALID)`（`2001`）。方法返回主图相对路径（如 `/upload/202611/{uuid}.jpg`），前端列表卡片按同前缀 `_thumb.jpg` 规则加载缩略图；同步提供 `deleteQuietly(List<String> relativePaths)` 供事务回滚后异步清理孤儿文件。

2、电子捐赠凭证目录（`certificate/yyyyMM/`，严禁配置 Tomcat 静态 URL 映射）：`saveCertificatePdf(String certNo, byte[] pdfBytes)` 按 `certNo` 固定格式（`^CLD(\d{6})\d+$`）解析年月子目录并落盘为 `{certNo}.pdf`；下载时仅由 `DonationController` 在鉴权与归属校验通过后调用 `readCertificateStream(String certNo, OutputStream out)` 流式写出。读取前强制校验 `certNo` 匹配白名单正则并验证 `targetPath.toAbsolutePath().normalize().startsWith(baseDir)` 杜绝路径遍历；文件不存在时抛出 `BizException(ErrorCode.DEPENDENCY_UNAVAILABLE)`（`5002`）提示前端重试生成。

## （六）Redis 客户端与键规范

全部键模板统一收口在 `com.csu.campusloop.config.RedisKey` 并加 `cl:` 前缀，所有 ID 参数类型为 `Integer`；`com.csu.campusloop.util.RedisHelper` 封装 `get`、`setex`、`zrevrange`、`zincrby`、`tryDecrQuotaLua`、`incrQuota`、`incrLoginFail` 等方法，写操作强制传入过期时间（不提供永不过期重载），所有读写均用 `try/catch` 包裹并在异常时记录 `warn` 日志返回降级默认值，严禁因 Redis 故障中断主业务。

下表前 6 项严格对应《03-01 需求开发概要设计说明书（V1.1）》第五章（五）核心业务键，第 7～8 项为详细设计阶段补充的登录防爆破与收藏运行期细化键（不改变 V1.1 核心业务键设计与 15 张表结构，Redis 不可用时自动降级）：

| 方法签名 | 生成键名 | 数据结构 | TTL | 用途与一致性说明 |
| --- | --- | --- | --- | --- |
| `RedisKey.userTag(Integer userId)` | `cl:tag:user:{userId}` | ZSet | 30 天 | 用户兴趣标签权重（浏览 +1、收藏 +3、发布 +5） |
| `RedisKey.hotItem(String campus)` | `cl:rank:hot:{campus}` | ZSet | 1 天 | 校区热门在售物品榜，推荐冷启动兜底 |

### 3、处理流程

登录认证主流程（`POST /api/auth/login`）：

1、Controller 经 `@Valid` 校验 `LoginDTO` 非空与长度（`username` 3～30 位、`password` 6～20 位），若传入非空 `role` 则校验其属于 `student / club / admin` 白名单，不合法抛出 `1001`。

2、Service 经 `RedisHelper` 查询 `RedisKey.loginFail(username)` 失败计数：若当前计数已达到 `5` 次且键未过期，直接抛出 `BizException(ErrorCode.LOGIN_FAILED, "登录失败次数过多，请 5 分钟后再试")`（`1004`）；Redis 异常时记录 `warn` 并降级放行。

3、调用 `UserMapper.selectByUsername(username)` 查询用户；若记录不存在，执行防爆破失败计数自增（TTL 15 分钟；满 5 次重设 TTL 为 5 分钟）并抛出 `BizException(ErrorCode.LOGIN_FAILED)`（`1004`）。

4、先调用 `PasswordUtil.matches(dto.getPassword(), user.getPassword())` 比对 BCrypt 哈希，再校验前端传入的非空 `role` 是否等于库中 `user.role`：任一不通过均执行防爆破计数自增并统一抛出 `ErrorCode.LOGIN_FAILED`（`1004`），防止通过不同错误码枚举账号存在性或角色。

5、密码与角色均校验通过后，校验 `Integer.valueOf(1).equals(user.getStatus())`：若为 `0`（已停用），不计入防爆破失败，直接抛出 `BizException(ErrorCode.ACCOUNT_DISABLED)`（`1005`）。

6、登录校验全部通过，清理 `cl:auth:fail:{username}` 计数，由 `AuthController` 获取或创建 `HttpSession` 后调用 `request.changeSessionId()` 轮换会话 ID 防会话固定，组装 `LoginUser` 写入 `SESSION_LOGIN_USER`，并按库中真实 `user.role` 计算 `redirect`（`student`→`/index`、`club`→`/club/donations`、`admin`→`/admin/dashboard`）返回 `LoginVO`，同步通过 `@OperLog` 异步记录登录审计日志。

受保护请求实时拦截与退出流程：

1、请求进入 `AuthInterceptor.preHandle` 后，先按“HTTP 方法 + 精确路径/纯数字正则”匹配白名单，命中则直接返回 `true` 放行。

2、未命中白名单时读取 `request.getSession(false)` 中的 `LoginUser`；为空则按 Ajax/页面区分返回 `Result.fail(ErrorCode.UNAUTHORIZED)`（`1002`）或 302 重定向 `/login`。

3、Session 有效时调用 `AuthService.getAuthState(loginUser.getUserId())` 实时查库：若返回 `null` 或 `!Integer.valueOf(1).equals(state.getStatus())`，立即调用 `session.invalidate()`，Ajax 返回 `Result.fail(ErrorCode.ACCOUNT_DISABLED)`（`1005`），页面请求重定向 `/login?disabled=1`。

4、若账号正常，将最新 `authStatus` 与 `role` 同步更新到 `LoginUser` 对象中；对 `POST` 写接口进一步执行 `Origin / Referer` 同源校验，不通过直接写出 `Result.fail(ErrorCode.FORBIDDEN)`（`1003`）。

5、调用 `POST /api/auth/logout` 时，拦截器先验证已登录态，Controller 触发 `@OperLog` 留痕后调用 `session.invalidate()` 清空服务端会话，返回 `Result.ok()`。

### 4、关键规则

1、密码校验与防枚举顺序：一律先验 BCrypt 密码与角色匹配，最后再检查 `user.status`，杜绝未认证者探测封禁名单；全站禁止明文密码入库或输出至任何响应与日志。

2、角色唯一真源与前端标签校验：前端登录页选择的角色标签仅作入口校验，若前端未传 `role` 则按库中角色登录；若前端传入了与库中不一致的 `role` 则按 `1004` 拒绝，绝不信任前端角色覆盖服务端权限。

3、停用账号旧会话即时失效：后台管理员在模块 12 停用某账号后，该账号已持有的任意旧 Session 在下一次访问受保护接口或写接口时即被实时查库拦截并销毁，无法继续提交业务操作。

4、未认证学生（`auth_status = 0` 或 `2`）写操作划界：已登录但未通过校园认证的学生账号允许浏览与执行账号自服务写接口（退出登录 `#02`、消息标已读 `#33`、修改个人资料 `#44`、修改密码 `#45`）；调用全部校园业务写接口（发布/编辑物品 `#03`、下架删除 `#04`、流转下单 `#07`、技能发布/邀约 `#12/#15`、快捐 `#19`、评价 `#25`、申诉 `#27`、举报 `#39`、活动报名 `#50`）时，由各业务 Service 入口调用 `PermissionUtil.checkAuthenticatedStudent(loginUser)` 统一拦截并返回 `1003`。

5、身份核验扩展预留：保留 `user.student_no`、`user.auth_status` 及 `cl:auth:code:{studentNo}`（TTL 5 分钟）验证码模型作为校园邮箱实名认证扩展点；课程演示期通过初始化 SQL 预置已认证模拟账号（密码均为 BCrypt 密文）满足全角色演示。

### 5、异常分支

| 异常场景 | 错误码 | 处理与提示语 |
| --- | --- | --- |
| 账号或密码为空、长度越界或 `role` 非白名单枚举 | `1001` | `@Valid` 或手动校验拦截，返回首条字段校验提示 |
| 未登录访问受保护接口或退出登录 | `1002` | Ajax 返回“请先登录”，页面请求重定向至 `/login` |
| 角色越权、未认证调用业务写接口或跨站 `Origin` 请求 | `1003` | 返回“无权执行该操作”或“请先完成校园身份认证” |
| 账号不存在、BCrypt 密码错误、所选角色与账号不符或触发 5 次防爆破冷却 | `1004` | 常规失败统一返回“账号或密码错误”；冷却期内返回“登录失败次数过多，请 5 分钟后再试” |
| 登录时检测到 `user.status = 0`，或已登录旧会话在拦截器中复核到账号已被停用 | `1005` | 销毁旧 Session 并返回“账号已被停用，请联系管理员” |

### 3、处理流程

发布或编辑物品合一流程（`POST /api/items`，核心写库步骤标注 `@Transactional(rollbackFor = Exception.class)`）：

1、权限与门槛前置校验：调用 `PermissionUtil.checkAuthenticatedStudent(current)` 校验已认证学生身份；查询用户最新 `credit_score`，若 `< 40` 直接抛 `2004`（信用观察期暂停发布），若 `40 <= score < 60` 则允许上限记为 `3`，否则上限记为 `10`。

2、内容合规与分类校验：校验 `categoryId` 对应分类存在且 `is_show = 1`（否则抛 `1001`）；调用 `SensitiveWordUtil.contains` 校验 `title`（4～40 字）与 `description`（≤ 500 字），命中敏感词抛 `1001` 并提示具体合规问题；按 `tradeMode` 联动校验：`exchange` 要求 `expectItem` 非空且 ≤ 100 字（`price` 归零 `BigDecimal.ZERO`），`consign` 要求 `price > 0` 且调用 `ItemMapper.selectAvgConsignPrice(categoryId)` 获取同类寄售均价，若均价有效则校验 `price <= avgPrice * 3`，若该分类尚无寄售样本则跳过 3 倍校验并校验 `price <= 50000.00`（超限均抛 `2002`）。

3、区分新增与编辑校验：
   若 `dto.getItemId() == null`（新发布）：调用 `ItemMapper.countActiveByOwner(current.getUserId())` 统计 `status IN (0, 1) AND is_deleted = 0` 的件数，达到当前允许上限时（信用受限 3 件抛 `2004`，正常 10 件抛 `2003`）立即拦截；校验 `images` 数量在 `1～5` 张（否则抛 `2001`）。
   若 `dto.getItemId() != null`（编辑）：查询目标物品（不存在或 `is_deleted=1` 抛 `2102`），调用 `PermissionUtil.checkOwner(current.getUserId(), item.getOwnerId())` 校验归属（越权抛 `1003`），校验当前 `status` 必须属于 `{0, 1, 4}`（`2` 锁定或 `3` 已完成抛 `2102`）；若物品原状态为 `4`（已下架）且本次编辑重提将回 `0`（待审核），同样执行上述在售+待审上限校验；校验 `keepImageUrls` 每一项均属于该 `itemId` 在 `item_image` 中的既有路径（防止越权引用他人物品图片，非法抛 `1003`），校验 `keepImageUrls.size() + newImages.size()` 在 `1～5` 张之间（否则抛 `2001`）。

4、图片校验压缩与磁盘落盘：遍历新上传的 `images` 逐张调用 `FileStorageService.saveItemImage(file)`（大小 → 扩展名 → 魔数 → 压缩主图与缩略图），收集本次新写入的相对路径列表 `savedPaths`；将 `keepImageUrls`（编辑态）与 `savedPaths` 按序合并为 `finalUrls`，首张即封面 `coverUrl`。

5、数据库事务写入（`@Transactional`）：若数据库写入发生任何异常，在 `catch` 或事务回滚回调中调用 `FileStorageService.deleteQuietly(savedPaths)` 清理本次新建孤儿文件。
   新发布时写入 `item`（`status = 0`、`view_count = 0`、`is_deleted = 0`、`cover_url = finalUrls.get(0)`），批量插入 `item_image`（`sort_no` 从 `0` 递增）。
   编辑时通过条件更新 `UPDATE item SET ..., cover_url = ?, status = 0 WHERE id = ? AND owner_id = ? AND status IN (0, 1, 4) AND is_deleted = 0` 保证并发下不会覆盖刚被锁定的物品（影响行数为 `0` 抛 `2102`），随后删除该 `item_id` 原 `item_image` 记录并按 `finalUrls` 重建排序记录。

6、事务提交后处理：触发 `@OperLog` 异步记录发布/编辑日志；若为新发布且登录态有效，以 `try/catch` 异步调用 `RedisHelper.zincrby(RedisKey.userTag(userId), categoryTag, 5)` 并续期 30 天（失败仅记 `warn` 不影响返回）；返回 `ItemSaveVO{itemId, status=0}`。

下架与逻辑删除流程（`POST /api/items/{id}/state`，`@Transactional`）：

1、校验 `action` 仅允许 `offShelf` 或 `delete`（否则抛 `1001`）；查询未删除物品记录（不存在抛 `2102`）并调用 `PermissionUtil.checkOwner` 校验本人归属（越权抛 `1003`）。

2、当 `action = "offShelf"` 时，校验当前 `status` 为 `0` 或 `1`，执行条件更新 `UPDATE item SET status = 4 WHERE id = ? AND owner_id = ? AND status IN (0, 1) AND is_deleted = 0`；影响行数为 `0`（如并发已被锁定或已完成）抛 `2102`。

3、当 `action = "delete"` 时，严禁删除锁定态物品，执行条件更新 `UPDATE item SET is_deleted = 1 WHERE id = ? AND owner_id = ? AND status != 2 AND is_deleted = 0`；影响行数为 `0` 抛 `2102`。记录 `@OperLog` 并返回 `ItemStateVO{itemId, status}`。

我的闲置分页与详情浏览流程（`GET /api/items/mine`、`GET /api/items/{id}`）：

1、`pageMine`：强制以当前 `current.getUserId()` 作为 `owner_id` 过滤条件，固定 `is_deleted = 0`，按可选 `status` 与 `create_time DESC` 经 `PageHelper.startPage` 分页查询并返回 `PageResult<ItemVO>`。

2、`detail`：按主键查询 `item` 与有序 `item_image` 列表；若记录不存在或 `is_deleted = 1` 直接抛 `2102`。

3、详情可见性判定：当 `status` 为 `0`（待审核）或 `4`（已下架）时，仅允许发布者本人（`current != null && current.getUserId().equals(item.getOwnerId())`）或管理员（`role="admin"`）查看，其余游客或他人统一抛 `1003`；`status` 为 `1 / 2 / 3` 允许公开查看。

4、热度与兴趣打标：仅当 `status == 1` 且非发布者本人浏览时，执行原子更新 `UPDATE item SET view_count = view_count + 1 WHERE id = ? AND status = 1 AND is_deleted = 0`，同时在 `current != null` 时以 `try/catch` 异步向 `cl:tag:user:{userId}` 累加浏览权重 `+1` 并续期 30 天（Redis 异常静默降级）。最终组装脱敏后的卖家昵称、信用分、信用等级、多图列表与 `isOwner` 标识返回 `ItemDetailVO`。

### 4、关键规则

1、图片合规与旧图防越权：图片数量严格限定 `1～5` 张、单张 `≤ 2MB`、魔数校验仅放行 JPG/PNG/WebP 并重编码剥离 EXIF；编辑时 `keepImageUrls` 必须校验全部归属当前 `itemId`，首图固定作为 `item.cover_url`（`sort_no = 0`）。

2、寄售价格与冷启动边界：寄售模式 `price` 采用 `BigDecimal` 且须 `> 0`；同分类存在在售/历史寄售样本时不得超过均价 3 倍，分类暂无样本时跳过 3 倍限制但限制 `≤ 50000.00` 元，交换模式忽略前端传价强制落 `0.00`。

3、发布上限与信用分分层门槛：在售数量统一按 `status IN (0, 1) AND is_deleted = 0` 统计，防止批量提交待审冲穿上限；信用分 `≥ 60` 上限 10 件（超限 `2003`），`40～59` 降为 3 件（超限 `2004`），`< 40` 暂停发布与重提（`2004`）。

4、状态机收敛与条件更新：物品状态迁移一律收口至 `ItemService.changeStatus` 或带前置状态条件的 SQL（`WHERE id = ? AND status = ? AND is_deleted = 0`），编辑非锁定态后强制回到 `0` 待审核重新过审；`status = 2`（锁定）禁止编辑、下架与逻辑删除。

5、逻辑删除与孤儿文件兜底：物品删除只更新 `is_deleted = 1`，绝不物理删除 `item` 或历史关联单据；事务回滚时异步清理当次新上传图片，防止磁盘泄漏。

### 3、处理流程

（1）发起流转单 `create`（`@Transactional(rollbackFor = Exception.class)`）

1、`@Valid` 校验入参格式，失败抛 `BizException(ErrorCode.PARAM_INVALID)`。

2、按 `itemId` 查目标物品：不存在、`is_deleted = 1` 或 `status != 1` 一律抛 `2102`（不区分“不存在”与“不可操作”，避免探测他人下架物品）。

3、`item.owner_id == current.getUserId()` 时抛 `2102`（禁止向本人下单）。

4、校验 `dto.tradeMode` 与 `item.trade_mode` 一致，不一致抛 `2102`（前端传递错误模式不得顺手改写物品属性）。

5、交换模式（`exchange`）：`offerItemId` 为空抛 `1001`；按 ID 查出换出物品，要求 `owner_id` 为当前用户、`status = 1`、`is_deleted = 0`、且 `id != itemId`，任一不满足抛 `2102`。

6、成对锁定（事务内，先目标后换出，固定顺序避免死锁）：

```java
// 目标物品：在售 -> 锁定
int locked = itemMapper.lockItem(itemId);          // UPDATE item SET status=2 WHERE id=? AND status=1 AND is_deleted=0
if (locked != 1) {
    throw new BizException(ErrorCode.ITEM_TAKEN);  // 2101 被抢先
}
// 交换模式再锁换出物品，失败则整个事务回滚，目标物品锁定一并撤销
if (isExchange) {
    int lockedOffer = itemMapper.lockItem(offerItemId);
    if (lockedOffer != 1) {
        throw new BizException(ErrorCode.ITEM_TAKEN); // 2101
    }
}
```

7、生成单号并插入单据：`order_status = 0`、`from_user_id = 当前用户`、`to_user_id = item.owner_id`、`verify_code` 留空（预约时才生成）。

8、事务提交后，经 `@TransactionalEventListener(phase = AFTER_COMMIT)` 异步向物品所有者写一条 `notify`（`notify_type = order`）；通知失败仅记 `warn`，不回滚锁单。

9、返回 `orderId`、`orderNo`、`orderStatus = 0`、`lockedItems`（目标 + 换出物品 ID 列表）。

（2）确认接单 `confirm`

1、查单据，不存在或当前用户既非 `from_user_id` 也非 `to_user_id` → `1003`；既非所有者又调用确认 → `1003`（仅 `to_user_id` 可确认）。

2、`OrderStatusEnum.canTransit(0, 1)` 为假 → `2102`（已确认、已取消、已违约均在此拦截，避免重复确认）。

3、条件更新 `UPDATE exchange_order SET order_status = 1 WHERE id = ? AND order_status = 0`，影响行数不等于 1 → `2102`。

4、事务提交后通知发起方“对方已接单，请预约面交”。

（3）取消流转 `cancel`

1、查单据并校验参与方 → `1003`。

2、仅 `0`（待确认）、`1`（已确认）、`2`（待面交）可取消，其余状态（`3`/`4`/`5`）→ `2102`。

3、条件更新 `UPDATE exchange_order SET order_status = 4, close_reason = ? WHERE id = ? AND order_status = ?`（带原状态），影响行数不等于 1 → `2102`。

4、成对解锁：目标物品 `2 -> 1`；交换模式下换出物品同样 `2 -> 1`。解锁用条件更新 `WHERE status = 2`，影响行数为 0 时记 `warn` 但不抛异常（物品可能已被后台下架，不应阻断取消）。

5、事务提交后通知对方并附取消原因。

（4）我的流转 `pageMine` / 详情 `detail`

1、`pageMine` 按 `roleType` 决定过滤列：`from` 用 `from_user_id = ?`，`to` 用 `to_user_id = ?`；`PageHelper.startPage` 紧跟单条查询。

2、`detail` 仅参与双方可读，非参与方 → `1003`；出参不含 `verify_code`（核销码只经二维码通道下发，见模块 05）。

### 4、关键规则

1、双模式状态机（越级一律 `2102`）：

| 当前 | 允许迁移 | 触发者 | 说明 |
| --- | --- | --- | --- |
| `0` 待确认 | `1` 已确认 / `4` 已取消 | 所有者 / 双方或超时 | 24 小时未接单由定时任务置 `4` |
| `1` 已确认 | `2` 待面交 / `4` 已取消 | 双方预约 / 双方或超时 | 48 小时未预约由定时任务置 `4` |
| `2` 待面交 | `3` 已完成 / `4` 已取消 / `5` 已违约 | 发起方核销 / 双方 / 超时 | 超预约 24 小时由定时任务置 `5` |
| `3` 已完成 | — | — | 终态，仅可评价 |
| `4` 已取消 | — | — | 终态，物品已解锁 |
| `5` 已违约 | — | — | 终态，物品已解锁，扣发起方积分 |

2、防重复抢单：锁单一律用 `WHERE status = 1` 的条件更新 + 影响行数判定，禁止“先 `select` 判断再 `update`”——两人同时下单时后者必然读到过期快照。`lockedItems` 放在同一事务，任一失败整体回滚，不会出现“目标锁了、换出没锁”的半锁状态。

3、固定加锁顺序：始终先锁目标物品、后锁换出物品，使两个互相交换的请求（A 换 B、B 换 A）按同一顺序竞争，避免死锁。

4、禁止向本人下单：`owner_id == 当前用户` 直接 `2102`，与“物品被锁定”共用同一错误提示，不暴露物品所有权细节。

5、锁定态物品不可编辑、不可删除：`item.status = 2` 时发布/编辑/下架接口一律 `2102`（该约束由模块 02 执行，本模块只负责置锁与解锁）。

6、单号幂等兜底：`order_no` 撞 `uk_order_no` 时由 `GlobalExceptionHandler` 捕获 `DuplicateKeyException` 返回 `2102`，不重试生成新号（防止重复提交产生两张单据）。

7、通知不参与事务：通知属可丢消息，一律 `AFTER_COMMIT` 异步发送；若与主事务同生共死，通知服务抖动会让锁单失败，得不偿失。

8、取消原因必填：`close_reason` 为空直接 `1001`，保证详情页与后台审计能看到取消理由。

### 5、异常分支

| 错误码 | 触发场景 | 提示语 |
| --- | --- | --- |
| `1001` | `itemId`/`tradeMode` 缺失、`closeReason` 为空、`message` 超 200 字、交换模式缺 `offerItemId` | 请完善必填信息 / 取消原因不能为空 |
| `1002` | Session 缺失或过期 | 请先登录 |
| `1003` | 非流转单参与方查看详情、非所有者调用确认 | 无权操作该流转单 |
| `1005` | 请求过程中账号被管理员停用 | 账号已停用，请联系管理员 |
| `2101` | 目标或换出物品的条件更新影响行数为 0（被他人抢先锁单） | 手慢了，该物品已被抢先锁定 |
| `2102` | 向本人下单、模式不一致、状态越级或重复确认、取消终态单据、操作锁定物品、单号冲突 | 当前状态不允许该操作 |

```java
public interface SkillService {

    SkillStatusVO save(SkillSaveDTO dto, LoginUser current);

    PageResult<SkillVO> page(SkillQuery query);

    SkillDetailVO detail(Integer id, LoginUser current);

    InviteResultVO invite(Integer id, SkillInviteDTO dto, LoginUser current);
```

### 3、处理流程

（1）发布 / 编辑 `save`

1、`skillId` 为空走新增：`@Valid` 校验 `skillName`（≤ 50 字）、`skillType ∈ {1,2}`、`level ∈ {入门, 熟练, 精通}`，非法 → `1001`。

2、新增前统计该用户同 `skill_type` 且 `status = 1` 的有效条数：`SELECT COUNT(*) FROM skill WHERE user_id = ? AND skill_type = ? AND status = 1`，`>= 3` 抛 `2201`。

3、插入记录，`status` 默认 `1`，返回 `skillId`、`status`。

4、`skillId` 非空走编辑：先按 ID 查记录，不存在或 `user_id != 当前用户` → `1003`；仅允许修改 `skillName`、`level`、`expectSkill`、`description`，`skill_type` 发布后不可改（否则可绕过 3 条上限）。

5、`status = 0` 即关闭：条件更新 `WHERE id = ? AND user_id = ?`，关闭后不再出现在大厅列表，已发出的邀约仍可在消息记录中查看。

（2）筛选分页 `page`

1、`PageHelper.startPage(page, pageSize)`，`pageSize` 由 `PageQuery` 强制裁剪至 ≤ 50。

2、固定过滤 `status = 1`，按 `skillType`、`level` 等值过滤；`keyword` 对 `skill_name` 与 `expect_skill` 做 `LIKE`，入参先经 `SensitiveWordUtil` 与 `%`/`_` 转义。

3、排序固定 `create_time DESC`，不暴露排序字段（大厅无“最热”需求，避免多一种白名单）。

（3）详情与互补判定 `detail`

1、按 ID 查详情，不存在或 `status = 0` → `2102`（已关闭技能不可查看详情，避免邀约入口残留）。

2、读取当前用户与发布者各自“我能提供（1）”与“我需要（2）”的技能名集合。

3、双向匹配：当前用户的“我需要”集合与发布者“我能提供”集合有交集 且 当前用户“我能提供”与发布者“我需要”有交集 → 标记 `complementary = true`，并在 `matchTags` 返回交集技能名，作为页面“高度互补”角标依据。

4、出参附发布人信用分与等级，便于判断是否值得交换。

（4）互换邀约 `invite`

1、查技能，不存在或 `status = 0` → `2102`。

2、`skill.user_id == 当前用户` → `2202`（不可邀约本人）。

3、事务内写入邀约记录（本模块只需 `notify` 一条站内通知即可承载，不单独建表；通知内容含技能名、邀约人与留言）。

4、`message` 超 200 字 → `1001`；为空则使用默认文案“对你的技能「XXX」很感兴趣，想和你互换”。

5、返回 `inviteSent = true`；通知写入失败抛 `5001` 并回滚（邀约必须送达才有意义，与订单通知的“可丢”策略相反）。

### 4、关键规则

1、同类有效技能上限 3 条：按 `user_id + skill_type + status = 1` 计数，编辑不增计数、关闭后释放名额；超限 `2201`。该规则落在 Service 而非数据库约束，因为“有效”是业务状态而非唯一性。

2、`skill_type` 发布后不可改：允许改类型等于绕过上限（先发 3 条“我能提供”，再改成“我需要”）。

3、不可邀约本人：`2202`，与“已关闭技能”共用同一入口校验顺序（先查存在与状态，再判本人），避免信息泄露。

4、已关闭技能不可见、不可邀约：详情与邀约统一返回 `2102`，列表侧直接过滤，防止前端缓存旧链接绕过。

5、互补判定只做名称交集：不做语义相似度计算，保证可解释——页面显示的具体技能名就是判定依据，避免“黑箱推荐”难以验收。

6、邀约通知必须入库：与订单通知不同，邀约的唯一产出就是通知，所以通知写失败即整体失败（`5001`），不允许“邀约成功但对方收不到”。

7、技能不占用物品锁：技能交换只做撮合与通知，不生成 `exchange_order`，因此不参与物品锁定状态机，避免与流转模块耦合。

### 5、异常分支

| 错误码 | 触发场景 | 提示语 |
| --- | --- | --- |
| `1001` | 技能名缺失或超长、`skillType`/`level` 取值非法、留言超 200 字 | 请检查填写内容 |
| `1002` | 未登录访问详情或邀约 | 请先登录 |
| `1005` | 账号已停用 | 账号已停用，请联系管理员 |
| `2102` | 技能不存在、已关闭、编辑他人技能 | 该技能已关闭或不存在 |
| `2201` | 同类有效技能已达 3 条 | 同类技能最多发布 3 条，请先关闭不再需要的技能 |
| `2202` | 邀约自己发布的技能 | 不能邀约自己 |

```java
public interface AppointmentService {

    /** 预约面交：1 -> 2，生成一次性核销码但不回传 */
    OrderAppointVO appoint(OrderAppointDTO dto, Integer orderId, LoginUser current);

    /** 发起方核销：2 -> 3，条件更新保证幂等，同事务内加分 */
    OrderVerifyVO verify(Integer orderId, OrderVerifyDTO dto, LoginUser current);

    /** 所有者取核销二维码：仅返回图片流，不返回明码 */
    byte[] qrcode(Integer orderId, LoginUser current);

    /** 三段超时巡检：0->4（24h）、1->4（48h）、2->5（超预约 24h） */
    int scanTimeout(LocalDateTime now);
}
```

### 3、处理流程

（1）预约 `appoint`（`@Transactional`）

1、查单据并校验参与方（仅 `from_user_id` / `to_user_id`）→ `1003`。

2、单据必须为 `1` 已确认状态，否则：`0` 未接单 → `2102`（提示“等待对方接单”）、`2/3` → `2102`（已预约/已完成）、`4/5` → `2104`。

3、校验预约时间：`appointTime` 必须晚于当前时间且落在 09:00–21:00 区间、分钟数为 `00` 或 `30`；不满足 → `1001`。

4、校验 `appointPlace` 属于 `campus-loop.pickup-points` 配置白名单，否则 → `1001`（不落库任意字符串，避免统计口径被污染）。

5、生成一次性核销码 `verify_code = IdUtil.nextVerifyCode()`（32 位，不可猜测）。

6、条件更新 `UPDATE exchange_order SET order_status = 2, appoint_time = ?, appoint_place = ?, verify_code = ? WHERE id = ? AND order_status = 1`，影响行数不等于 1 → `2102`（并发重复预约）。

7、响应不返回 `verify_code`：出参仅 `orderId`、`orderStatus`、`appointTime`、`appointPlace`。核销码只进二维码，确保“看到码的人不能核销、能核销的人拿不到码”。

8、事务提交后通知对方预约时间与地点。

（2）获取二维码 `qrcode`

1、查单据，校验当前用户为 `to_user_id`（物品所有者），否则 → `1003`（发起方取码即自核销，必须拦死）。

2、单据必须为 `2` 待面交且 `verify_code` 非空，否则 → `2102`。

3、`QrCodeUtil.generatePng("CL-VERIFY:" + verify_code, 300)` 生成 PNG，`Content-Type: image/png` 直接写响应流，禁走 JSON。

（3）核销 `verify`（`@Transactional`）

1、查单据，校验当前用户为 `from_user_id`，否则 → `1003`（所有者核销即自核销）。

2、状态判定：`3` 已完成 → `2102`（重复核销，且不得重复加分）；`5` 已违约 → `2104`；`0/1` → `2102`（未预约）。

3、核销码校验：`dto.verifyCode` 与库中 `verify_code` 做常量时间比较，不一致 → `2103`。

4、条件更新：`UPDATE exchange_order SET order_status = 3, finish_time = NOW() WHERE id = ? AND order_status = 2`，影响行数不等于 1 → `2102`。这是幂等的唯一闸口，并发两个核销请求只有一个能拿到 1。

5、同事务内更新物品：目标物品 `2 -> 3` 已完成；交换模式下换出物品同样 `2 -> 3`。

6、同事务内调用模块 07 `CreditService.addScore(fromUserId, +5, "finish", orderId)` 与 `CreditService.addScore(toUserId, +5, "finish", orderId)`：写 `credit_log` 并原子更新 `user.credit_score`。同一数据库本地事务，保证“核销成功但没加分”不会发生。

7、事务提交后（`AFTER_COMMIT`）通知双方“已核销，请在 7 天内互评”，并写入模块 10 评价提醒。

8、返回 `orderId`、`orderStatus = 3`、`finishTime`。

（4）超时巡检 `scanTimeout`（`OrderTimeoutTask` 每小时执行）

1、三类扫描分别执行，互不影响：

| 段 | 扫描条件 | 处置 |
| --- | --- | --- |
| 待确认 | `order_status = 0 AND create_time < now - 24h` | 置 `4` 已取消，原因“超时未接单”，成对解锁 |
| 待预约 | `order_status = 1 AND create_time < now - 48h` | 置 `4` 已取消，原因“超时未预约”，成对解锁 |
| 待面交 | `order_status = 2 AND appoint_time < now - 24h` | 置 `5` 已违约，成对解锁，扣发起方 10 分 |

2、每单独立事务：先做条件更新（`WHERE order_status = 原状态`），影响行数为 1 才继续解锁与扣分；为 0 说明已被用户操作抢先，直接跳过——绝不覆盖用户主动操作的结果。

3、扣分调用 `CreditService.addScore(fromUserId, -10, "timeout", orderId)`，`ref_id` 记订单号，便于申诉回溯；同一订单因条件更新守卫只会扣一次。

4、返回本次处置单数，写入定时任务日志；单次处理上限 500 单，避免长事务拖垮连接池。

### 4、关键规则

1、角色隔离防自核销：出码仅 `to_user_id`、核销仅 `from_user_id`，两者在 Controller 之外还要在 Service 再校验一次（拦截器只校验登录态，不区分单据角色）。这是本模块最关键的一条——任一方能在交付前独自完成核销，整个履约约束就失效了。

2、核销码不可回传、不可枚举：`verify_code` 为 32 位 UUID 派生值，只经二维码下发；`OrderDetailVO` 与预约响应都不含该字段。

3、幂等靠条件更新而非查询判断：`2 -> 3` 的条件更新是唯一闸口，重复提交影响行数为 0 → `2102`，且第 6 步加分根本不会执行，从根上杜绝重复加分。

4、三段超时统一归口：`0` 超 24h、`1` 超 48h 均无责取消（用户未推进流程）；`2` 超预约 24h 判违约并默认扣发起方 10 分（按《03-01》第 206 行口径），物品所有者爽约或归责不明时，发起方可经模块 07 提交单次申诉，由管理员复核撤回扣分或转扣违约方。

5、超时不越权：定时任务只处理“仍未推进”的单据，且以条件更新为准；用户刚操作完的单据不会被定时任务覆盖。

6、二维码内容带前缀：`CL-VERIFY:` 前缀用于区分本系统码与外部二维码，扫描后仅解析前缀匹配的载荷，降低误扫风险。

7、预约粒度与时段：09:00–21:00、30 分钟一档，与自提点值守时间对齐；不做跨天预约，避免“预约在闭馆时段”导致必然违约。

### 5、异常分支

| 错误码 | 触发场景 | 提示语 |
| --- | --- | --- |
| `1001` | 预约时间缺失/已过/不在 09:00–21:00/非整半点、自提点不在白名单、核销码为空 | 请选择有效的面交时间与自提点 |
| `1003` | 非参与方预约、发起方取二维码、所有者调用核销 | 无权执行该操作 |
| `1005` | 账号已停用 | 账号已停用，请联系管理员 |
| `2102` | 未接单即预约、重复预约、重复核销、已完成或已取消单据再操作 | 当前状态不允许该操作 |
| `2103` | 核销码不匹配或已被使用 | 核销码无效，请重新扫码 |
| `2104` | 超过预约时间 24 小时已被判违约关闭 | 该流转单已超时关闭，如有异议可提交申诉 |

### 3、处理流程

快捐申请流程（`POST /api/donations`，`@Transactional(rollbackFor = Exception.class)`）：

1、调用 `PermissionUtil.checkAuthenticatedStudent(current)` 校验已认证学生身份；查询目标社团账号（`user.id = clubId AND role = 'club' AND status = 1`），不存在或已停用抛 `1001`。

2、查询 `item` 记录：若不存在、`is_deleted = 1`、非当前用户所有（`owner_id != current.getUserId()`）或 `status != 1`（非在售），抛出 `BizException(ErrorCode.ITEM_NOT_DONATABLE)`（`2203`）。

3、调用 `ItemService.changeStatus(itemId, 1, 2)` 执行条件更新锁单：若影响行数为 `0`（并发已被他人下单或重复提交快捐），事务回滚并抛出 `BizException(ErrorCode.ITEM_TAKEN)`（`2101`）。

4、插入 `donation` 记录（`donor_id = current.getUserId()`、`club_id = dto.getClubId()`、`audit_status = 0`、`audit_remark = dto.getRemark()`）。

5、事务提交后异步调用模块 10 `NotifyService` 通知目标社团有新捐赠待审核，记录 `@OperLog` 并返回 `{donationId, auditStatus=0}`。

捐赠台账隔离查询流程（`GET /api/donations`）：

1、按当前 `LoginUser.role` 强制注入数据隔离条件：`role = "student"` 时固定限定 `donor_id = current.getUserId()`；`role = "club"` 时强制覆盖 `query.setClubId(current.getUserId())`（完全忽略前端传入的 `clubId` 参数，若前端显式传入其他社团 ID 可直接拒绝返回 `1003`）；`role = "admin"` 允许按全部或指定 `clubId` 筛选。

2、紧邻 `PageHelper.startPage` 执行分页查询并封装返回 `PageResult<DonationVO>`。

社团审核与 PDF 解耦生成流程（`POST /api/donations/{id}/audit`，核心状态变更标注 `@Transactional(rollbackFor = Exception.class)`）：

1、调用 `PermissionUtil.checkRole(current, "club")` 校验社团身份；查询 `donation` 记录（不存在抛 `2102`），调用 `PermissionUtil.checkClubAccess(current, donation.getClubId())` 校验本社团归属（越权抛 `1003`）。

2、若 `dto.getPass()` 为 `false`（驳回）：先校验 `dto.getAuditRemark()` 非空（为空抛 `1001`）；执行条件更新 `UPDATE donation SET audit_status = 2, audit_user = ?, audit_time = NOW(), audit_remark = ? WHERE id = ? AND club_id = ? AND audit_status = 0`（影响行数为 `0` 抛 `2102`）；调用 `ItemService.changeStatus(donation.getItemId(), 2, 1)` 将物品解锁回在售态（影响行数为 `0` 回滚抛 `2102`）。

3、若 `dto.getPass()` 为 `true`（通过）：调用 `IdUtil.nextCertNo()` 生成全局唯一凭证号（格式 `CLD` + `yyyyMM` + 6 位流水，如 `CLD2026110019`）；执行条件更新 `UPDATE donation SET audit_status = 1, audit_user = ?, audit_time = NOW(), audit_remark = ?, certificate_no = ? WHERE id = ? AND club_id = ? AND audit_status = 0`（影响行数为 `0` 抛 `2102`；若触发 `uk_certificate_no` 唯一索引冲突则重生成重试最多 3 次）；调用 `ItemService.changeStatus(donation.getItemId(), 2, 3)` 将物品置为已完成态；同事务内调用模块 07 `CreditService.addScore(donation.getDonorId(), +5, "donation", donation.getId(), "公益捐赠审核通过")` 发放捐赠诚信积分。

4、事务提交后解耦执行两项后置动作：第一，构造公开验真链接（如 `{baseUrl}/donations/verify?certificateNo={certNo}`），经 `QrCodeUtil.generatePng` 生成验真二维码与 `PdfUtil.renderDonationCert` 渲染中文字体 PDF，调用 `FileStorageService.saveCertificatePdf(certNo, pdfBytes)` 落盘至非静态目录 `certificate/yyyyMM/{certNo}.pdf`（若渲染或磁盘写入失败，仅捕获异常记 `error` 日志，绝不回滚已提交的审核结果）；第二，调用 `NotifyService` 通知捐赠人审核结论，并通过 `@OperLog` 留痕。

鉴权流式下载与公开脱敏验真流程（`#22`、`#23`）：

1、鉴权下载（`GET /api/donations/{id}/certificate`）：在写入任何响应头前调用 `prepareCertificateForDownload(id, current)`——校验记录存在且 `audit_status == 1`（否则 `2102`）、校验当前用户为捐赠人（`donor_id`）或接收社团（`club_id`，越权抛 `1003`）；检查目标 PDF 是否已存在，若此前异步渲染失败缺失文件，按需触发一次即时补偿渲染落盘（补偿仍失败抛 `5002`）。全部校验通过后，Controller 再设置 `Content-Type: application/pdf` 与 `Content-Disposition: attachment; filename="{certNo}.pdf"`，调用 `FileStorageService.readCertificateStream(certNo, response.getOutputStream())` 流式输出。

2、公开脱敏验真（`GET /api/donations/verify`）：校验 `certificateNo` 非空且匹配正则 `^CLD\d{12}$`（非法抛 `1001`）；按 `uk_certificate_no` 查库，不存在或 `audit_status != 1` 抛出 `2102`（“凭证编号无效或未生效”）；查获有效记录后对捐赠人真实姓名执行脱敏（保留首字，其余字符替换为 `**`，如“林**”），仅返回 `DonationVerifyVO` 六个最小脱敏字段。

### 4、关键规则

1、社团数据严格隔离：社团账号仅可查看、审核与下载归属本社团（`club_id`）的捐赠记录，越权一律返回 `1003`，SQL 层的 `club_id` 条件由后端 Session 强制注入。

2、锁单与解锁原子成对：快捐申请成功即将物品从 `1` 锁为 `2`；社团驳回时必须填写驳回理由并同事务解锁回 `1`；审核通过则同事务置物品为 `3` 已完成，严禁出现“审核通过但物品仍锁定”或“驳回后物品未解锁”。

3、PDF 渲染解耦与非静态保护：PDF 渲染放在数据库事务提交之后执行，必须注册嵌入中文字体防止方框乱码；失败不回滚业务，下载接口支持即时补偿生成；`certificate/` 目录严禁配置 Tomcat 静态资源映射。

4、公开验真最小字段白名单：`#23` 接口仅暴露 `certificateNo`、`itemTitle`、`clubName`、`donorMasked`、`auditTime`、`valid`，禁止返回捐赠人学号、学院、完整姓名及服务端本地路径。

```java
    AppealCreateVO submitAppeal(CreditAppealDTO dto, LoginUser current);
```

### 3、处理流程

原子积分变动流程（`CreditService.addScore`，`@Transactional(rollbackFor = Exception.class)`，默认 `Propagation.REQUIRED` 融入调用方主事务）：

1、参数校验：`userId`、`changeValue`（非 0）与 `reasonType` 非空，否则抛 `1001`。

2、先查变动前分值档位（用于后续判断是否跨等级发通知），紧接着执行数据库原子更新 `UPDATE user SET credit_score = GREATEST(0, credit_score + #{changeValue}) WHERE id = #{userId}`（最低托底 0 分且校验影响行数 = 1，严禁先查出旧值在内存中加减后再回写）。

3、写入 `credit_log` 流水记录（`user_id`、`change_value`、`reason_type`、`ref_id`、`remark`），流水写入失败则整笔事务回滚，确保余额与流水绝对一致。

4、查询更新后的最新 `credit_score` 并经 `resolveLevel` 判定等级；若发生等级变动或触发扣分/申诉回补，注册事务提交后回调（`TransactionSynchronization.afterCommit`）异步调用 `NotifyService` 发送 `credit` 类型站内通知。

双向履约评价流程（`POST /api/reviews`，`@Transactional(rollbackFor = Exception.class)`）：

1、调用 `PermissionUtil.checkAuthenticatedStudent(current)` 校验已认证学生；查询 `exchange_order` 记录（不存在抛 `2102`），校验 `order_status == 3`（已完成，否则抛 `2102`）。

2、调用 `PermissionUtil.checkOrderParticipant(current, order)` 校验当前用户为交易双方之一（越权抛 `1003`），据此确定被评价人 `toUserId`（若当前为 `from_user_id` 则评 `to_user_id`，反之亦然）。

3、校验评价时效：计算 `order.finish_time` 至当前时间的间隔，超过 `7 * 24` 小时直接抛出 `BizException(ErrorCode.REVIEW_EXPIRED)`（`2302`）；对 `content` 执行 `SensitiveWordUtil` 敏感词检查（命中抛 `1001`）。

4、组装 `Review` 插入数据库，由联合唯一索引 `uk_order_from(order_id, from_user_id)` 并发防重；业务层显式捕获 `DuplicateKeyException` 并转抛 `BizException(ErrorCode.REVIEW_DUPLICATE)`（`2301`）。

5、好评防刷与加分：当 `dto.getScore() >= 4` 时，查询最近 7 天内 `credit_log`（或 `review`）中同一对用户 `(from_user_id, to_user_id)` 已触发好评加分的次数；若为 `0`（7 天内首次），同事务调用 `CreditService.addScore(toUserId, +3, "good_review", order.getId(), "收到流转单好评")`；若已加过分则正常保留评价但不重复计分，防止双方互刷积分。

积分流水查询与单次扣分申诉流程（`#24`、`#27`）：

1、流水与申诉回显（`GET /api/credits/logs`）：读取当前用户最新 `credit_score` 与等级，分页查询本人 `credit_log`；提取当前页所有 `change_value < 0` 的 `credit_log.id` 集合，批量查询 `report` 表中 `reporter_id = current.getUserId() AND report_type = '积分申诉'` 的工单，按前缀 `[creditLogId={id}]` 映射每条扣分记录的 `appealStatus`（`null` 未申诉、`0` 待复核、`1` 已通过、`2` 已驳回），组装 `CreditSummaryVO` 返回。

2、提交申诉（`POST /api/credits/appeals`，`@Transactional`）：校验 `credit_log` 存在且 `user_id == current.getUserId()`（越权抛 `1003`）且 `change_value < 0`（正分不可申诉抛 `2102`）；校验 `report` 表中不存在同 `reporter_id` 且前缀匹配 `[creditLogId={creditLogId}]` 的既有申诉记录（已申诉过抛 `2102`）；插入 `report` 表（`item_id = NULL`、`reporter_id = current.getUserId()`、`report_type = "积分申诉"`、`report_content = "[creditLogId=" + creditLogId + "] " + dto.getReason()`、`handle_status = 0`），返回 `{reportId, handleStatus=0}`；后续由模块 12 管理员在 `#40/#41` 统一复核，通过时调用 `CreditService.addScore(userId, +abs(changeValue), "appeal_refund", creditLogId, remark)` 补充回补流水并保留原扣分流水。

### 4、关键规则

1、数据库原子更新：全站任何积分变动必须收敛至 `CreditService.addScore`，使用 `credit_score = GREATEST(0, credit_score + ?)` 原子更新（最低托底 0 分）并与 `credit_log` 写操作处于同一本地事务，禁止内存先查后改。

2、四档信用等级与治理联动：`≥ 90` 优秀、`75～89` 良好、`60～74` 一般、`40～59` 受限（模块 02 在售上限降为 3 件）、`< 40` 观察期（暂停发布 7 天）；所有积分规则统一由 `CreditRuleEnum` 配置化管理。

3、一单一评与短期防刷：`review` 表以 `uk_order_from(order_id, from_user_id)` 强制防重；仅订单完成后 7 天内开放评价；同对用户 7 天内多次互评只计首次好评加分。

4、申诉复用 `report` 表不扩第 16 表：单条扣分流水严格限申诉 1 次，通过结构化前缀 `[creditLogId={id}]` 与 `report_type='积分申诉'` 精准回溯；复核通过只追加 `appeal_refund` 正分流水，严禁删除或篡改原始扣分流水。

| --- | --- | --- |
| 评分不在 1～5、评价超 500 字、命中敏感词或申诉理由为空/超 300 字 | `1001` | 返回对应字段校验或合规提示 |
| 未登录查询本人积分流水、提交评价或提交申诉 | `1002` | 拦截器返回“请先登录” |
| 非流转单双方提交评价、申诉他人积分流水或未认证学生提交评价 | `1003` | 返回“无权执行该操作” |

| 流转单核销完成已超过 7 天 | `2302` | 返回“已超过 7 天评价期限” |

| `SortWhitelist` | `enums` / `config` | `Map<String, String>` 排序白名单：`latest`→`create_time DESC`、`hot`→`view_count DESC`、`price_asc`、`price_desc` |

### 2、方法设计

| 方法签名 | 对应接口 | 事务 |
| --- | --- | --- |
| `ItemSearchResultVO search(ItemSearchQuery query)` | `GET /api/items` | 否（只读） |
| `List<CategoryTreeVO> categoryTree()` | `GET /api/categories/tree` | 否（只读） |

```java
public interface ItemSearchService {

    /** 多条件检索：固定过滤在售未删除，排序走白名单，空结果返回兜底列表 */
    ItemSearchResultVO search(ItemSearchQuery query);

    /** 启用状态的二级分类树（一次查询后在内存装配，避免 N+1） */
    List<CategoryTreeVO> categoryTree();
}
```

### 3、处理流程

（1）检索 `search`

1、`@Valid` 校验：`pageSize` 裁剪至 1–50、`page >= 1`；`minPrice > maxPrice` 直接交换两者（宽容处理而非报错，价格区间本无方向语义）；`minPrice`/`maxPrice` 为负 → `1001`。

2、排序白名单映射：`sort` 经 `SortWhitelist` 转成 SQL 片段，未命中则回落 `latest`；前端传入的字符串永远不进 SQL，只有 `Map` 里的固定值可以拼进 `ORDER BY`。

3、固定过滤：`status = 1 AND is_deleted = 0`，由 Mapper 的 `<where>` 前置写死，不接受调用方覆盖。

4、动态条件：`categoryId`（含其二级子分类，用 `IN`）、`conditionLevel`、`campus`、`tradeMode` 等值匹配；`keyword` 对 `title`、`description` 做 `LIKE '%kw%'`，并对 `%`、`_`、`\` 转义。

5、`PageHelper.startPage(page, pageSize)` 后紧跟单条查询，返回 `PageResult<ItemCardVO>`。

6、热门词写入：检索有结果时以 `try/catch` 调 `RedisHelper` 对 `cl:search:hot` 执行 `ZINCRBY keyword 1` 并续期 7 天；失败仅记 `warn`，不影响返回。

7、空结果兜底：`total == 0` 且传了 `categoryId` 时，追加一次同分类在售热门查询（`ORDER BY view_count DESC LIMIT 4`），放 `fallbackList` 供前端渲染“同类热门”；无 `categoryId` 则不兜底，返回空列表（搜索“不存在的东西”不该被强行塞结果）。

（2）分类树 `categoryTree`

1、一次查询 `SELECT * FROM category WHERE is_show = 1 ORDER BY parent_id, sort_no`。

2、内存中按 `parent_id = 0` 取一级、其余归入对应父节点；两级封顶，出现三级数据直接忽略（防止字典误配导致前端嵌套渲染错乱）。

3、结果可按 `campus` 配置缓存，但本版不做缓存——分类字典仅 60 行级，直查比维护缓存失效更简单。

### 4、关键规则

1、排序白名单防注入：`ORDER BY` 是 MyBatis 唯一无法用 `#{}` 参数化的位置，因此只允许从固定 `Map` 取值，禁止 `ORDER BY ${sort}` 直传。

2、组合索引命中：分类 + 在售态走 `idx_cate_status(category_id, status)`，校区 + 在售态走 `idx_campus_status(campus, status)`；因此 `categoryId`/`campus` 条件必须与 `status` 同时出现才能命中组合索引（固定过滤保证了这一点）。

3、只在售可见：`status = 1 AND is_deleted = 0` 是硬过滤，不做“管理员可见全部”的分支——后台用独立接口（模块 12），避免一套 SQL 两种语义。

4、分页稳定：`ORDER BY` 末尾补 `id DESC` 兜底，防止 `view_count` 相同的记录在翻页时重复或遗漏。

5、关键词最短长度：`keyword` 去空格后长度 < 2 视为未传，避免单字导致全表 `LIKE` 扫描。

6、兜底不掩盖空态语义：只有传了分类才兜底，且明确放在 `fallbackList` 字段而非混入 `list`，前端能区分“搜到了”与“没搜到但给你看同类”。

### 5、异常分支

| 错误码 | 触发场景 | 提示语 |
| --- | --- | --- |
| `1001` | `page`/`pageSize` 非法、价格为负、金额格式错误 | 查询条件有误 |
| `5001` | 分类树查询异常、SQL 执行异常 | 系统繁忙，请稍后重试 |

> Redis 写热门词失败不对外暴露错误码：该操作不影响检索结果，仅记 `warn` 日志（不满足“依赖不可用”`5002` 的判定，因为主链路未降级）。

```java
public interface RecommendService {

    /** 首页为你推荐 12 条；未登录/冷启动/Redis 异常自动降级 */

    /** 收藏/取消收藏，并异步累加标签权重 +3 */
    Boolean toggleFavorite(Integer itemId, LoginUser current);

    /** 异步打标：浏览 +1、收藏 +3、发布 +5 */
    void addTagWeight(Integer userId, Integer categoryId, int weight);
}
```

### 3、处理流程

（1）推荐列表 `recommend`

1、未登录：跳过个性化，直接走降级链第 2 级（校区热门榜）。

2、读缓存：`RedisHelper.get(RedisKey.recCache(userId))`；命中且非空则直接返回（缓存内 12 条，前端“换一批”在本地轮换，不再打接口）。

3、未命中 → 读标签：`ZREVRANGE cl:tag:user:{userId} 0 4 WITHSCORES` 取权重 TOP 5 的分类 ID。

4、召回与排序：按 5 个分类批量查在售物品（`status = 1 AND is_deleted = 0`），按 `view_count DESC` 排序，取前 12 条；同分类内按权重高的优先，保证“最常看的分类”排在前面。

5、生成推荐理由：对每条结果，取其所命中分类的名称拼文案——「因为你常看「数码电子」」，权重来自第一优先分类时用「你最近关注」。文案由服务端生成而非前端拼接，保证多端一致。

6、回填缓存：`SETEX cl:rec:cache:{userId} 600 <json>`，10 分钟；序列化用 Jackson，VO 标注 `@JsonIgnoreProperties(ignoreUnknown = true)`。

（2）降级链（三级）

| 级别 | 触发条件 | 数据来源 | 前端表现 |
| --- | --- | --- | --- |
| 1 | 标签非空、Redis 正常 | `cl:tag:user` TOP 5 召回 | “为你推荐”+ 个性化理由 |
| 2 | 未登录、新用户无标签、标签为空 | `cl:rank:hot:{campus}` ZSet（读失败再退 3） | “同校区热门”，附“换一批” |
| 3 | Redis 整体不可用 | 直接查 `item`：`status=1` 按 `view_count DESC` + `campus` 过滤 `LIMIT 12` | “同校区热门”（与 2 同文案，用户无感） |

（3）收藏切换与打标 `toggleFavorite`

1、查物品，不存在或非在售 → `1001`/`2102` 由模块 02 的口径统一，本接口只需保证 `itemId` 合法。

2、事务内切换收藏状态（本版统一以 Redis Set 键 `cl:fav:user:{userId}` 承载，维持 15 张表不扩表，已纳入第三章（六）运行期细化键表）。

3、返回 `favorited` 布尔值。

4、事务提交后异步调用 `addTagWeight(userId, item.categoryId, +3)`；取消收藏不回减权重（权重代表兴趣强度，不随一次取消归零）。

（4）异步打标 `addTagWeight`

1、`@Async` 执行，`ZINCRBY cl:tag:user:{userId} {weight} {categoryId}`。

2、随后 `EXPIRE cl:tag:user:{userId} 2592000`（30 天），实现“每次行为后续期”。

3、全程 `try/catch`，失败仅 `warn`——打标丢失影响下一次推荐质量，不影响本次请求。

4、浏览详情在模块 02 的详情接口内触发 `+1`，发布在模块 02 审核通过后触发 `+5`，三处统一调用 `TagService`，权重常量集中定义在 `RecommendConst`。

### 4、关键规则

1、权重口径固定：浏览 `+1`、收藏 `+3`、发布 `+5`，与《03-01》第 258 行一致；权重只增不减，靠 30 天 TTL 自然衰减，避免维护“减权重”的复杂逻辑。

2、缓存 TTL 10 分钟：过短会导致首页每次都走召回查询，过长会让新发布物品迟迟不出现；10 分钟是“可见性”与“数据库压力”的折中。

3、所有 Redis 读写必须 `try/catch`：这是《03-01》非功能设计（三）的硬要求；本模块是 Redis 依赖最重的模块，降级链三级保证“Redis 全挂首页仍可用”。

4、推荐理由必须可解释：理由文案只能来自“实际命中的标签分类名”，禁止生成“猜你喜欢”这类无信息量文案——验收时要能指着一条推荐说出为什么推它。

5、“换一批”在缓存内轮换：接口固定返回 12 条，前端本地轮换，不打接口；否则每次点击都触发一次召回，缓存形同虚设。

6、打标与业务解耦：打标是异步旁路，任何失败不得影响收藏、浏览、发布的主流程（与模块 04 邀约通知的“必须成功”策略相反，因为打标是本模块的旁路增强）。

7、推荐不返回敏感字段：`RecommendItemVO` 不含 `owner_id`、`description` 全文，减少一次请求的数据量与越权探测面。

### 5、异常分支

| 错误码 | 触发场景 | 提示语 | 降级行为 |
| --- | --- | --- | --- |
| `1001` | `itemId` 非法或缺失 | 参数错误 | — |
| `1002` | 未登录调用收藏接口 | 请先登录 | — |
| `1005` | 账号已停用 | 账号已停用，请联系管理员 | — |
| `5001` | 数据库查询异常（三级降级全部失效） | 系统繁忙，请稍后重试 | 首页展示空态与“最新发布”列表 |
| 不抛出 | Redis 连接失败或超时 | — | 记 `warn`，按降级链 2/3 返回，接口仍返回 `code=0` |

> 说明：Redis 故障按《03-01》要求走降级而非报 `5002`——`5002` 保留给“核销/凭证等主链路依赖不可用且无法降级”的场景（本模块主链路可降级，故不适用）。

## （十）站内消息与通知（模块 10）

### 1、类与职责
`MessageController` 从 Session 获取当前用户 ID，校验请求参数，以公共 `Result<T>` 返回结果。`MessageService` 定义查询、标记已读、统计和模板发送方法；`MessageServiceImpl` 实现归属校验、事务控制和模板渲染。`NotifyMapper` 读写 MySQL 的 `notify` 表。`NotifyTemplateEnum` 为每种业务事件定义通知类型、标题、正文和必填占位符。`NotifyVO` 对外提供 id、title、content、notifyType、isRead、createTime。

### 2、方法设计
| 入口 | Service 方法 | 输入与返回 |
| --- | --- | --- |
| `GET /api/messages` | `list(Integer userId, String notifyType, Integer isRead, Integer page, Integer pageSize)` | 两个筛选条件均可省略；返回 `PageResult<NotifyVO>`。 |
| `POST /api/messages/read` | `markRead(Integer userId, Integer notifyId, Boolean all)` | 单条模式提供正整数 notifyId；全部模式仅传 all=true。返回含 unreadCount 的对象。 |
| `GET /api/messages/unread-count` | `countUnread(Integer userId)` | 无客户端入参；返回含 unreadCount 的对象。 |
| 业务模块内部调用 | `send(Integer recipientId, NotifyTemplateEnum template, Map<String,String> arguments)` | 调用方提供接收人和模板参数，无返回值；本模块不反向调用业务模块。 |

### 3、处理流程
1. 生成通知。业务事务提交成功后，按模板检查必填参数，渲染标题与正文，独立事务写入接收人、类型和未读状态。业务事务回滚时跳过发送。标题最多 100 字符，正文最多 500 字符。
2. 分页查询。以 `user_id = 当前用户` 为固定条件，再追加类型和阅读态筛选。`PageHelper.startPage` 后立即执行查询，按 create_time、id 双降序排列。页码默认 1，每页默认 12 条，上限 50。
3. 标记已读。单条模式在事务内按 id 和 user_id 查询归属，再以相同条件和 `is_read=0` 更新为 1；本人已读消息直接成功。全部模式仅更新当前用户的未读行。两种模式均在更新后统计当前用户剩余未读数并返回。

### 4、关键规则
类型限定为 order、audit、credit、system；阅读态 0 表示未读，1 表示已读。未读统计按 `user_id` 和 `is_read=0` 计数，复用索引 `idx_notify_user`。顶部红点每 30 秒请求一次统计接口，直接显示服务端返回值。重复或并发标记同一条消息只改变一次状态：起初有 3 条未读且期间无新消息时，连续两次标记同一条后均返回 2。

### 5、异常分支
公共拦截器在三个接口执行前校验身份。Session 缺失或过期返回 `1002`「未登录」；已登录用户被停用时销毁旧 Session，返回 `1005`「账号已停用」。单条标记找不到属于当前用户的目标时统一返回 `1003`「无权限」，避免暴露他人消息是否存在。筛选值非法或标记模式参数矛盾时按公共参数校验返回 `1001`，不执行更新。模板参数缺失、渲染超长或通知写入失败时记录模板、接收人 ID 与失败原因，不记录消息正文，不回滚已提交的主业务。

## （十一）统计分析与数据看板（模块 11）

### 1、类与职责
`DashboardController` 接收管理员查询和导出请求，校验校区、起止日期，分别返回公共响应或文件流。`DashboardService` 统一计算指标，供页面和导出复用。`StatDailyMapper` 读写日统计并查询分类分布；`StatDailyTask` 每日汇总前一自然日，支持指定日期重算。`StatDailyVO` 表示一个日期、一个校区的指标；`DashboardVO` 包含区间 KPI、逐日趋势、分类占比、双模式占比及漏斗四个阶段的数量。

### 2、方法设计
| 入口 | 方法与结果 |
| --- | --- |
| `GET /api/admin/dashboard` | `query(String campus, LocalDate startDate, LocalDate endDate)` 返回 `DashboardVO`，控制器封装为 `Result<DashboardVO>`。 |
| `GET /api/admin/dashboard/export` | `export(String campus, LocalDate startDate, LocalDate endDate, OutputStream out)` 使用同一查询口径，通过 Apache POI 写出 .xlsx 文件流。 |
| 每日定时任务 | `aggregate(LocalDate statDate)` 对指定自然日分别生成各校区及全校统计，按日期和校区唯一键写入。 |

### 3、处理流程
1. 日汇总。从统计日零点取到次日零点之前。发布按物品发布时间计数，流转意向按发起时间计数，交换和寄售按同批流转单的 trade_mode 分组；成交按核销完成时间计数，捐赠按审核通过时间计数。流转单按目标物品归属校区统计。违约归入实际转为违约的日期，浏览归入访问发生日期。
2. 写入。按 `uk_date_campus(stat_date,campus)` 执行 `INSERT ... ON DUPLICATE KEY UPDATE`，将可重算指标覆盖为本次计算值。全校行使用 `campus='ALL'`。查询全校时仅取 ALL 行；查询单校区时只取该校区。
3. 展示。按含首尾两天的日期区间读取日表，累计发布、成交、审核通过捐赠及违约数，按日期输出发布和成交趋势。分类占比另查同期同校区发布物品，按 category_id 分组并除以发布总数。交换与寄售分别除以两种模式单数之和。漏斗依次展示 publish_count、view_count、order_count、finish_count 的区间合计；浏览单位为次，意向和成交单位为单，属于期间业务量。
4. 导出。以相同筛选参数获取看板结果，将校区、日期范围、指标和逐日明细写入工作簿。使用 Apache POI 的 SXSSFWorkbook 分批写行并释放临时文件；下载文件名包含校区和日期范围。

### 4、关键规则
区间违约率取 `SUM(default_count) / SUM(order_count)`，以百分比展示。两天分别有 1/2、0/8 笔违约时，区间结果为 10%。分母为零时比率返回 0；已完成汇总且无业务的日期返回零值，页面展示统一空态。

日指标重跑必须能追溯到统计日。现有物品 view_count 只保存累计次数，订单当前状态也不能确定实际转为违约的日期。建议由浏览处理和违约状态转换在业务写入成功时，于同一事务按日期更新校区行及 ALL 行的对应计数；违约仅在条件更新成功一次时计入。采用此方案时，日任务仅覆盖可从业务明细重算的列，保留已累积的 view_count、default_count，避免重跑清零或重复累加。此写入约定需与对应模块负责人对齐；缺少采集记录的历史区间不能作为零业务验收。立项 Plan B 启用时可暂缓本模块，看板与导出均独立于流转主流程。

### 5、异常分支
两个接口均先校验管理员身份：会话缺失或过期返回 `1002`「未登录」，角色不符返回 `1003`「无权限」。导出生成失败且响应尚未提交时返回 `5001`「系统异常」；若文件流已开始发送，则终止下载并记录失败，避免将 JSON 拼入工作簿。日任务失败时回滚本次事务并记录日期与校区，修复后按原统计日重跑。

## （十二）后台审核与违规处置（模块 12）

### 1、类与职责
`AdminAuditController` 接收待审查询及审核决定；`ReportController` 分别接收用户举报、管理员查询与处置请求；`AdminDictController` 校验字典类型和操作。`AdminAuditService` 管理物品状态转换，`ReportService` 按工单类型执行处罚或申诉复核，`ReportMapper` 负责工单新增、筛选和条件更新。`ItemAuditDTO` 携带物品 ID 列表、决定及原因，`ReportSubmitDTO` 携带举报对象、类型和说明，`ReportHandleDTO` 携带处理状态、动作及备注。经办人从 Session 取得，所有接口 ID 均为 Integer。

### 2、方法设计
| 接口 | 方法、参数与成功结果（由公共 Result 封装） |
| --- | --- |
| `GET /api/admin/items/pending` | listPending(campus, categoryId, page, pageSize)：按校区、分类筛选待审物品，返回 PageResult<PendingItemVO>。 |
| `POST /api/admin/items/audit` | audit(itemIds, pass, reason)：审核一个或多个物品，返回 processedCount。 |
| `POST /api/reports` | submit(itemId, reportType, reportContent)：按登录用户创建普通举报，返回 reportId、handleStatus。 |
| `GET /api/admin/reports` | listReports(handleStatus, reportType, page, pageSize)：按状态和工单类型筛选，返回 PageResult<ReportVO>。 |
| `POST /api/admin/reports/{id}/handle` | handle(id, handleStatus, action, remark)：处理一个待办工单，返回 reportId、handleStatus。 |
| `POST /api/admin/dicts/{dictType}` | maintain(dictType, op, payload)：对白名单内字典执行对应操作，返回操作结果或列表。 |

### 3、处理流程
1. 物品审核。校验 itemIds 非空并去重，驳回时校验原因。按 ID 升序在同一事务内把待审物品更新为在售（1）或已下架（4）；任一记录已离开待审状态则整批回滚。通过时逐件调用模块 07 记发布积分；驳回时向发布者说明原因。提交成功后通过模块 10 通知发布者。
2. 工单分流。普通举报按允许的违规类型校验，reporter_id 取会话用户，说明不超过 500 字，初始 handle_status=0。积分申诉由模块 07 的专用入口建单，report_type 为“积分申诉”，report_content 关联原 credit_log.id 与理由；普通举报入口拒绝该保留类型。
3. 管理员处置。在事务中读取工单，按 id 和 handle_status=0 条件写入目标状态、handle_user、handle_time。影响一行才执行对应动作：违规核实可下架物品、扣 15 分、限制发布或停用账号；根据已核实的对象执行，无法确定被处置账号时不得处罚。申诉通过时核对原扣分流水与申请人，通过模块 07 追加对应回补流水，保留原流水。驳回只记录结果。处置成功为 1，驳回为 2；动作失败则工单状态与业务变更一并回滚。事务提交后通知申请人。
4. 字典维护。分类、成色、自提点、积分规则分别校验操作和字段。删除分类前在事务内检查其物品及子分类引用；若存在引用，保留原记录并返回冲突。对分类的引用写入与删除使用一致的锁定顺序，避免检查后又新增引用。

### 4、关键规则
五个 /api/admin/ 接口限 admin，普通举报接口要求有效登录。停用账号在处置事务中写入 user.status=0；此后即使用户持有旧 Session，AuthInterceptor 也会在下一次受保护请求进入控制器前复核状态并销毁会话。所有操作经模块 14 的 `@OperLog` 留痕，记录经办人、目标、动作及结果。两名管理员同时处理同一工单时仅允许一次状态转换和一次处罚或回补。

### 5、异常分支
| 错误码与提示 | 触发条件及结果 |
| --- | --- |
| 1001 参数错误 | 拒绝空审核列表、缺少驳回原因、非法字典类型或与工单不符的处置动作，数据保持原状。 |
| 1002 未登录 | Session 缺失或过期，提示重新登录。 |
| 1003 无权限 | 非管理员访问后台队列或提交后台操作，拦截请求。 |
| 1005 账号已停用 | 账号已停用但旧会话仍发起受保护请求，销毁会话并终止处理。 |
| 2102 状态冲突 | 物品已审核、工单已处置或待删除分类仍被引用；提示刷新记录或先解除引用，重复请求不再记分。 |

### 3、处理流程
1. 查看。认证拦截器核验会话及账号状态后，服务按本人 ID 查询展示字段和信用概览，将敏感标识脱敏后返回。个人中心 [UI-19] 的名片链接至信用档案 [UI-14]。切换“我的发布、我的流转、我的捐赠、我的技能”时按本人身份分别分页加载；个人资料响应只返回概览。

## （十四）操作日志审计（模块 14）

### 1、类与职责
`@OperLog` 在业务入口声明操作类型；`OperLogAspect` 在调用前后收集审计信息。`OperLogService` 接收已脱敏的记录并异步写入，同时提供分页查询；`OperLogMapper` 负责向 oper_log 插入记录及按条件检索。`OperLogController` 提供管理员只读入口，`OperLogVO` 返回账号、角色、操作类型、脱敏摘要、时间及客户端 IP。

### 2、方法设计
| 入口或方法 | 输入与结果 |
| --- | --- |
| `@Around` 环绕通知 | 接收连接点和注解，仅执行一次目标方法，保留原返回值或异常；将操作结果、耗时及上下文交给记录服务。 |
| `OperLogService.appendAsync` | 接收独立的脱敏记录快照，由线程池执行 Mapper 单行插入。 |
| `GET /api/admin/audit-logs` | 管理员可传 userName、operType、startTime、endTime、page、pageSize，返回 `Result<PageResult<OperLogVO>>`。 |

### 3、处理流程
1. 在登录、发布、审核、流转、核销、捐赠审核、积分调整及账号处置入口标注操作类型。切面在请求线程读取账号、角色、客户端 IP 和开始时间；登录成功后从新会话补取身份，未识别身份时允许 user_id 为空。
2. 目标调用结束时计算耗时，按允许的字段组装目标标识、结果与耗时摘要。涉及事务的成功变更在提交后投递成功记录，回滚按失败记录。记录快照携带操作发生时间，不把请求或 Session 对象传给后台线程。
3. 后台线程将快照映射到 user_id、user_name、role、oper_type、oper_desc、oper_time、ip_address 并插入。查询时按指定账号、类型及时间区间组合筛选，按 oper_time、id 倒序稳定分页，默认每页 12 条、上限 50 条。后台导航 [UI-17] 的详情抽屉复用选中行的脱敏数据。

### 4、关键规则
先筛选和脱敏，再限制 oper_desc 总长度为 255 字符。摘要仅保留定位操作所需的信息；学号按展示规则遮蔽，密码、密码哈希、核销码和会话凭据均不采集。查询视图只读，无编辑、删除控件及对应接口。队列拒绝任务或异步插入失败时，以应用日志记录操作类型和失败原因，避免再次触发审计切面。审计故障不改变业务结果：管理员已提交的账号停用继续生效，原业务异常也须原样传播。

### 5、异常分支
查询前由公共鉴权组件检查会话及管理员角色。Session 缺失或过期返回 `1002`「未登录」；已登录的非管理员访问返回 `1003`「无权限」，两种情形均不读取日志。管理员筛选后无匹配记录时返回成功及空分页。

```java
package com.csu.campusloop.service;

import com.csu.campusloop.dto.ActivityQuery;
import com.csu.campusloop.dto.ActivitySaveDTO;
import com.csu.campusloop.vo.ActivityDetailVO;
import com.csu.campusloop.vo.ActivityJoinVO;
import com.csu.campusloop.vo.ActivitySaveVO;
import com.csu.campusloop.vo.ActivityVO;
import com.csu.campusloop.vo.LoginUser;
import com.csu.campusloop.vo.PageResult;

public interface ActivityService {
    ActivitySaveVO save(ActivitySaveDTO dto, LoginUser current);
    PageResult<ActivityVO> page(ActivityQuery query);
    ActivityDetailVO detail(Integer activityId, LoginUser current);
    ActivityJoinVO join(Integer activityId, LoginUser current);
}
```

### 3、处理流程

活动发布/编辑/结束流程（`POST /api/activities`，`@Transactional(rollbackFor = Exception.class)`）：

1、调用 `PermissionUtil.checkRole(current, "admin", "club")` 校验发布权限；校验 `endTime` 晚于 `startTime`、`quota >= 1`（非法抛 `1001`）。

2、若 `activityId == null`（新发布）：插入 `activity` 表（`remain_quota = quota`、`creator_id = current.getUserId()`、`status` 默认 `1` 报名中或 `0` 草稿、`is_deleted = 0`）。

3、若 `activityId != null`（编辑或结束）：查库校验存在且 `is_deleted = 0`（否则 `2102`）；若当前用户为 `club` 角色则额外校验 `creator_id == current.getUserId()`（越权 `1003`）；已结束活动（`status == 3`）禁止重新编辑回报名中（抛 `2102`）；若调整了 `quota`，新 `quota` 不得小于已报名人数（`quota - remain_quota`，否则抛 `1001`）并同步重算 `remain_quota`。

4、事务提交后：若目标状态为 `1`（报名中），以 `try/catch` 调用 `RedisHelper.setex(RedisKey.activityQuota(activityId), ttlSeconds, String.valueOf(remainQuota))` 预热名额预筛键（TTL 设为 `endTime + 24h`）；若状态切为 `3`（已结束），同步清理预筛键并汇总报名人数写入审计日志。

活动报名高并发防超卖流程（`POST /api/activities/{id}/join`）：

1、前置身份校验：调用 `PermissionUtil.checkAuthenticatedStudent(current)` 校验已认证学生身份。

2、Redis 前置预筛（事务外）：调用 `RedisHelper.tryDecrQuotaLua(RedisKey.activityQuota(activityId))` 执行原子 Lua 脚本（若键存在且值 `> 0` 则 `DECR` 返回 `1`；若键存在且值 `<= 0` 则返回 `0`；若键不存在或 Redis 连接异常则返回 `-1`）。
   当返回 `0` 时，直接抛出 `BizException(ErrorCode.ACTIVITY_FULL)`（`2401`），挡住已满额流量；
   当返回 `1` 时，标记局部标志 `redisDecremented = true`，进入第 3 步 MySQL 事务；
   当返回 `-1`（缓存未预热或 Redis 宕机）时，记录 `warn` 日志并保持 `redisDecremented = false`，直接穿透进入第 3 步 MySQL 唯一真源事务。

3、MySQL 唯一真源事务（`doJoinInDb`，标注 `@Transactional(rollbackFor = Exception.class)`）：
   步骤 3.1：按主键查询 `activity` 记录，校验 `is_deleted == 0`、`status == 1`（报名中）且当前时间早于 `end_time`，不满足抛 `2102`。
   步骤 3.2：先执行带条件锁的原子名额扣减：`UPDATE activity SET remain_quota = remain_quota - 1 WHERE id = #{activityId} AND status = 1 AND is_deleted = 0 AND remain_quota > 0`；若影响行数为 `0`，说明名额已耗尽或状态已变，立即抛出 `BizException(ErrorCode.ACTIVITY_FULL)`（`2401`）。
   步骤 3.3：调用 `IdUtil.nextJoinNo()` 生成唯一报名凭证号（`CLJ` + `yyyyMMdd` + 6 位流水），插入 `activity_join(activity_id, user_id, join_no, status=1)`。若该学生此前已报名，MySQL 触发联合唯一索引 `uk_activity_user(activity_id, user_id)` 抛出 `DuplicateKeyException`，本地事务立即回滚（步骤 3.2 扣减的 `remain_quota` 自动复原，绝不出现“重复报名却白扣 1 个名额”），并转抛 `BizException(ErrorCode.ACTIVITY_ALREADY_JOINED)`（`2402`）。
   步骤 3.4：查询最新 `remain_quota` 返回 `ActivityJoinVO{joinId, joinNo, remainQuota}`。

4、异常回滚与 Redis 预筛回补（事务外 `catch` 块）：只要 `redisDecremented == true` 且第 3 步抛出任何异常（包括重复报名 `2402`、活动已结束 `2102` 或数据库异常，但不包括确认已满 `2401`），在 `catch` 块中立即调用 `RedisHelper.incrQuota(RedisKey.activityQuota(activityId))` 回补被预扣的 1 个预筛计数（`try/catch` 保护，失败仅记 `warn`），随后将原业务异常重新抛出。

5、事务提交后：异步调用 `NotifyService` 发送报名成功与凭证号通知，并经 `@OperLog` 记录报名留痕。

### 4、关键规则

1、名额一致性唯一真源：无论 Redis 是否在线，活动剩余名额始终以 MySQL `activity.remain_quota` 及同一事务内的条件更新为唯一真源；Redis 仅作高并发前置拦截层，彻底消除双路径计数分裂和超卖隐患。

2、防重与回滚闭环：`uk_activity_user` 联合唯一索引保证单人单活动仅能成功报名一次；重复报名或异常触发事务回滚时，MySQL 名额自动还原且同步回补 Redis 预筛计数。

3、状态机与权限：`activity.status` 严格遵循 `0 草稿 → 1 报名中 → 2 进行中 → 3 已结束`，仅 `1` 态允许报名；社团账号仅可维护本人发布的活动，管理员可维护全校活动。

4、Plan B 裁剪边界：本模块为低耦合外围扩展模块，不反向侵入模块 01～14；若期末开发周期紧张，按《01-01 项目立项书（V1.1）》Plan B 经组长确认可整体暂缓，不影响交易与快捐两条核心演示链路。

### 5、异常分支

| 异常场景 | 错误码 | 处理与提示语 |
| --- | --- | --- |
| 活动名称/地点缺失、`endTime <= startTime`、`quota < 1` 或新名额小于已报名人数 | `1001` | 拒绝保存并返回对应字段校验提示 |
| 未登录访问发布活动或报名接口 | `1002` | 拦截器返回“请先登录” |

# 五、数据库详细设计

## （一）设计约定

1、库与字符集：库名固定 `campus_loop`，默认字符集 `utf8mb4`、排序规则 `utf8mb4_general_ci`（MySQL 5.7 兼容），存储引擎统一 `InnoDB`、行格式 `DYNAMIC`。

2、主键与业务 ID：15 张表主键一律 `int NOT NULL AUTO_INCREMENT`，与 Java `Integer` 一一对应；接口层 ID 参数同为 `Integer`，禁止 `long`/`String` 混用，避免 MyBatis 类型映射错位。

3、金额：仅 `item.price` 涉及金额，统一 `decimal(10,2) DEFAULT 0.00`，Java 侧 `BigDecimal` 以 `RoundingMode.HALF_UP` 保留 2 位；禁止 `double`/`float`（浮点误差会使“寄售价 ≤ 同类均价 3 倍”的比对失准）。

4、时间：统一 `datetime`；`create_time` 默认 `CURRENT_TIMESTAMP`，`update_time` 附 `ON UPDATE CURRENT_TIMESTAMP` 交由数据库维护，业务代码不手工赋值，避免应用服务器时区与数据库不一致。

5、状态：一律 `tinyint`，取值含义写入列 `COMMENT`；用字符串存状态会破坏组合索引选择性，也使 `UPDATE ... WHERE status = ?` 的条件更新失去意义。

6、逻辑删除：仅历史业务主表 `item`、`activity` 保留 `is_deleted`；其余单据表不设逻辑删除，防止历史流水被“消失”而无法审计。

7、命名规范：表名与字段名小写下划线；普通索引 `idx_`、唯一索引 `uk_`、外键 `fk_`，索引名直接体现字段组合（如 `idx_cate_status`），便于 `GlobalExceptionHandler` 按 `DuplicateKeyException` 的索引名映射错误码（`uk_order_from` → `2301`、`uk_activity_user` → `2402`）。

8、建表顺序：`user` → `category` → `item` → `item_image` → 其余业务表 → `stat_daily` / `activity` / `activity_join`。全库仅 `item.owner_id`、`item_image.item_id` 两个物理外键，故必须先建被引用表。

9、MyBatis 映射：`mybatis-config.xml` 开启 `mapUnderscoreToCamelCase=true`；VO 聚合查询使用显式 `resultMap`，禁止 `SELECT *`，避免后续加字段撑大结果集。

10、表来源：15 张表 = 12 张沿用《项目开发文档说明书》表名与字段名（`user` 至 `oper_log`）+ 3 张本次新增（`stat_daily`、`activity`、`activity_join`），字段与《03-01 需求开发概要设计（V1.1）》第五章（二）逐列一致，无增删改。

容量估算：以 10 万条物品为基线，按各表平均行宽加权（`item` 约 1.2KB、`notify` 与 `oper_log` 约 0.5KB、其余 0.2～0.6KB）估算，数据总量约 1.3GB；叠加主键、唯一索引与组合索引（约 0.8 倍开销），两年总占用约 2.2～2.6GB。单机 MySQL 5.7 下该量级全表扫描仍在秒级以内，故检索类查询依赖组合索引而非分区，不引入分库分表。

增长最快的两张表是 `oper_log`（后台每次操作一条）与 `notify`（每单 3～5 条），二者合计占总量约 70%，因此按上表设定 90 天 / 180 天的归档窗口；`stat_daily` 按天预聚合，用 1,500 行换掉了看板对 `item`、`exchange_order` 的实时全量聚合。

## （六）Redis 键落地规范

沿用本文档第三章（六）的约定：所有键由 `RedisKey` 生成、统一 `cl:` 前缀、全部带 TTL，读写一律 `try/catch` 降级，禁止因缓存故障中断主业务。

```java
package com.csu.campusloop.config;

/**
 * Redis 键生成器：全部键统一 cl: 前缀，ID 参数统一 Integer。
 * TTL 常量集中在此，禁止业务代码散落硬编码。
 */
public final class RedisKey {

    private static final String PREFIX = "cl:";

    private RedisKey() {
    }

    /** 用户标签权重 ZSet，成员为 categoryId */
    public static String userTag(Integer userId) {
        return PREFIX + "tag:user:" + userId;
    }

    /** 校区热门物品榜 ZSet，成员为 itemId，score 为热度 */
    public static String hotItem(String campus) {
        return PREFIX + "rank:hot:" + campus;
    }

    /** 个性化推荐结果缓存（JSON） */
    public static String recCache(Integer userId) {
        return PREFIX + "rec:cache:" + userId;
    }

    /** 全校热门检索词 ZSet */
    public static String hotSearch() {
        return PREFIX + "search:hot";
    }

    /** 活动名额预筛计数 */
    public static String activityQuota(Integer activityId) {
        return PREFIX + "act:quota:" + activityId;
    }

    /** 校园邮箱核验验证码 */
    public static String authCode(String studentNo) {
        return PREFIX + "auth:code:" + studentNo;
    }
}
```

| 键模板 | 结构 | 序列化方式 | TTL | 写入时机 | 降级行为 |
| --- | --- | --- | --- | --- | --- |
| `cl:tag:user:{userId}` | ZSet | `StringRedisTemplate.opsForZSet()`，成员为分类 ID | 30 天（每次写后续期） | 浏览 +1、收藏 +3、发布 +5 | 读失败返回空集，推荐退化为热门榜 |
| `cl:rank:hot:{campus}` | ZSet | 同上，成员为物品 ID | 1 天 | 发布、成交时更新热度 | 读失败直接查 `item` 按 `view_count` 取 TOP 12 |
| `cl:rec:cache:{userId}` | String | `ObjectMapper` 序列化 `List<RecommendItemVO>` | 10 分钟 | 推荐接口未命中时回填 | 读失败视为未命中，重算后回填 |
| `cl:search:hot` | ZSet | 成员为检索词 | 7 天 | 检索接口命中结果时累加 | 写失败仅记 warn，不影响检索返回 |
| `cl:act:quota:{activityId}` | String | 纯整数字符串 | 活动结束后 24 小时 | 报名前预筛 | 读失败跳过预筛，直接以 MySQL 条件更新为准 |
| `cl:auth:code:{studentNo}` | String | 纯字符串验证码 | 5 分钟 | 发送校园邮箱验证码 | 读失败按“验证码已过期”提示重新获取 |

落地要点：

1、序列化统一：ZSet 成员与值一律用字符串，避免 JDK 序列化产生不可读的二进制成员（`redis-cli` 无法排查）；对象缓存用 Jackson 转 JSON，并在 `RecommendItemVO` 上标注 `@JsonIgnoreProperties(ignoreUnknown = true)`，防止后续加字段导致反序列化失败。

2、TTL 必须显式设置：`RedisHelper` 的写方法签名强制传入 TTL（`set(key, value, Duration)`），不提供无 TTL 的重载，从 API 层面杜绝键永不过期。

3、降级模板（所有调用点统一形态，禁止裸调用）：

```java
public <T> T getOrDegrade(String key, Supplier<T> loader, Supplier<T> fallback) {
    try {
        String json = stringRedisTemplate.opsForValue().get(key);
        if (json != null) {
            return objectMapper.readValue(json, new TypeReference<T>() { });
        }
    } catch (Exception e) {
        log.warn("Redis 读取失败，降级处理，key={}", key, e);
        return fallback.get();
    }
    return loader.get();
}
```

4、活动名额以 MySQL 为准：`cl:act:quota` 仅做高并发前置预筛（快速挡掉大部分超额请求），最终扣减仍走 `UPDATE activity SET remain_quota = remain_quota - 1 WHERE id = ? AND remain_quota > 0` 的原子条件更新，校验影响行数为 1，防止缓存与库不一致时超卖。`stat_daily` 同理，缓存只加速展示，日统计以库表数据重算为准。

# 六、接口详细设计

## （一）公共约定

本平台全部 50 个 RESTful 接口路径、HTTP 方法、权限角色与入出参摘要已在《03-01 需求开发概要设计说明书（V1.1）》第四章（三）冻结，本章不再重复罗列 50 条接口清单，重点明确编码期必须遵守的协议细则、两层参数校验契约与统一错误码枚举映射：

| 约定项 | 编码细则 |
| --- | --- |
| 路径与方法 | 统一前缀 `/api`，资源名小写复数；只读查询用 `GET`，新增、状态变更与逻辑删除统一用 `POST` |
| 媒体类型 | `GET` 用 Query String；JSON 写接口用 `application/json;charset=UTF-8`；物品发布/编辑（`#03`）因含多图上传使用 `multipart/form-data` |
| 统一响应体 | JSON 接口 HTTP 状态码固定 `200`，响应体为 `Result<T>{code, msg, data}`；`#18`（PNG）、`#22`（PDF）、`#36`（Excel）三个流式下载接口成功直接写字节流，鉴权/校验失败则在写响应头前交由全局异常处理器返回 JSON |
| 分页协议 | 请求统一继承 `PageQuery{page=1, pageSize=12}`（上限 `50`）；响应统一为 `PageResult<T>{total, list, pages, page, pageSize}`（对齐概要设计 `PageInfo<T>{total, list, pages}` 核心三字段并补回显当前页参数） |
| 鉴权与同源 | 基于 `HttpSession`（`SESSION_LOGIN_USER`）鉴权，拦截器对非白名单请求实时查库复核 `user.status`（停用销毁旧会话返 `1005`），对 `POST` 写接口叠加 `Origin/Referer` 同源校验（跨站返 `1003`） |
| 幂等与并发 | 写接口严禁依赖前端防抖作为唯一防重手段，后端必须依托条件更新（校验影响行数 = 1）与数据库唯一索引兜底 |

## （二）参数校验规则

全站接口实行两层校验：Controller 层通过 Jakarta Validation（`@Valid`、`@NotBlank`、`@NotNull`、`@Size`、`@DecimalMin`、`@Min`/`@Max`）拦截格式与边界错误（统一返 `1001`）；Service 层负责状态机、归属权限、敏感词与数据库约束等业务语义校验（按域返 `1003`/`2xxx`）：

| DTO 对象 | 对应接口 | Controller 注解校验（格式层） | Service 业务语义校验（规则层） |
| --- | --- | --- | --- |

# 七、关键流程时序

本章梳理系统最易出现并发竞争、数据撕裂或依赖故障的四条核心链路，明确每一步的数据变化、事务边界与降级路径。

## （一）以物易物全流程（含角色隔离核销）

### 1、参与方与前置条件

| 代号 | 角色 | 对应字段 | 本流程中的权限边界 |
| --- | --- | --- | --- |
| A | 发起方（学生） | `exchange_order.from_user_id` | 可下单、可取消、唯一可核销、可评价 |
| B | 物品所有者 | `exchange_order.to_user_id` | 可接单、可取消、唯一可取核销码、可评价 |
| I₁ | 目标物品 | `item.id = exchange_order.item_id` | 由 B 发布，`status = 1` 在售 |
| I₂ | 换出物品 | `item.id = exchange_order.offer_item_id` | 由 A 发布，`status = 1` 在售 |
| M₇ | 模块 07 诚信积分 | `CreditService` | 被模块 05 单向调用，不反向依赖 |
| M₁₀ | 模块 10 站内消息 | `NotifyService` | 横切底座，仅被调用 |

前置条件：A、B 均 `auth_status = 1` 且 `status = 1`；I₁、I₂ 均 `status = 1 AND is_deleted = 0`；I₁ 的 `trade_mode = exchange`。

### 2、阶段一：发起与成对锁单

| 步 | 发起方 | 接收方 | 动作 | 事务 |
| --- | --- | --- | --- | --- |
| 1 | A（浏览器 `[UI-07]`） | `OrderController` | `POST /api/orders`：`itemId=I₁`、`tradeMode=exchange`、`offerItemId=I₂`、`message` | — |
| 2 | `OrderController` | `OrderService.create` | `@Valid` 校验；取 Session `LoginUser` | 事务外 |
| 3 | `OrderServiceImpl` | `ItemMapper` | 查 I₁ 与 I₂，校验在售、非本人、模式一致、I₂ 归属 A | 只读 |
| 4 | `OrderServiceImpl` | `ItemMapper.lockItem(I₁)` | `UPDATE item SET status=2 WHERE id=? AND status=1 AND is_deleted=0` | 事务内 |
| 5 | 同上，影响行数=0 | — | 抛 `BizException(ErrorCode.ITEM_TAKEN)`，事务回滚 | 回滚 |
| 6 | `OrderServiceImpl` | `ItemMapper.lockItem(I₂)` | 同条件更新换出物品；影响行数=0 同样 `2101` 并回滚（I₁ 锁定一并撤销） | 事务内 |
| 7 | `OrderServiceImpl` | `ExchangeOrderMapper.insert` | 插入单据：`order_status=0`、`order_no=CL+日期+序号`、`verify_code=NULL` | 事务内 |
| 8 | 事务提交 | — | 锁单完成 | 提交点 |
| 9 | `OrderServiceImpl` | `NotifyService`（模块 10） | `AFTER_COMMIT` 异步通知 B“有人想换你的物品” | 事务外 |

关键点：第 4–7 步必须在同一个事务内。若拆成两个事务，会出现“目标物品已锁、换出物品未锁”的半锁状态，该物品将既不能被别人下单、也无法被 A 用于其他交换，只能等 24 小时超时任务解锁。

### 3、阶段二：接单确认

| 步 | 发起方 | 接收方 | 动作 | 事务 |
| --- | --- | --- | --- | --- |
| 10 | B（`[UI-08]`） | `OrderController` | `POST /api/orders/{id}/confirm` | — |
| 11 | `OrderServiceImpl` | `ExchangeOrderMapper` | 校验参与方身份（B 必须是 `to_user_id`，否则 `1003`） | 只读 |
| 12 | 同上 | `ExchangeOrderMapper` | `UPDATE exchange_order SET order_status=1 WHERE id=? AND order_status=0` | 事务内 |
| 13 | 同上，影响行数=0 | — | 抛 `2102`（已确认/已取消/已违约） | 回滚 |
| 14 | `OrderServiceImpl` | `NotifyService` | `AFTER_COMMIT` 通知 A“对方已接单，请在 48 小时内预约” | 事务外 |

### 4、阶段三：预约与出码（角色隔离起点）

| 步 | 发起方 | 接收方 | 动作 | 事务 |
| --- | --- | --- | --- | --- |
| 15 | A 或 B（`[UI-09]`） | `OrderController` | `POST /api/orders/{id}/appointment`：`appointTime`（09:00–21:00 整半点）、`appointPlace`（自提点白名单） | — |
| 16 | `AppointmentServiceImpl` | — | 校验：参与方、状态必须为 `1`、时间在未来且合法、地点在白名单 | 只读 |
| 17 | 同上 | `IdUtil.nextVerifyCode()` | 生成 32 位一次性核销码 | 事务外 |
| 18 | `AppointmentServiceImpl` | `ExchangeOrderMapper` | `UPDATE ... SET order_status=2, appoint_time=?, appoint_place=?, verify_code=? WHERE id=? AND order_status=1` | 事务内 |
| 19 | 同上，影响行数=0 | — | 抛 `2102`（并发重复预约） | 回滚，`verify_code` 作废 |
| 20 | `AppointmentServiceImpl` | — | 出参不含 `verify_code`，仅返回时间与地点 | — |
| 21 | B | `OrderController` | `GET /api/orders/{id}/qrcode`：校验 `to_user_id`，`QrCodeUtil` 生成 `CL-VERIFY:{code}` 的 PNG 流 | 只读 |
| 22 | 同上，非 B 调用 | — | 抛 `1003`；单据状态非 `2` 抛 `2102` | — |

关键点：第 20 步是整个角色隔离设计的核心——核销码只存在于二维码图像里，接口响应中永不出现。因此“能看到码的人（A）无法从接口拿到码，能调用取码接口的人（B）不能提交核销”，任一方都无法在交付前独自完成闭环。

### 5、阶段四：核销（幂等闸口）

| 步 | 发起方 | 接收方 | 动作 | 事务 |
| --- | --- | --- | --- | --- |
| 23 | A 当面扫码 | `OrderController` | `POST /api/orders/{id}/verify`：`verifyCode` 来自扫码解析 | — |
| 24 | `AppointmentServiceImpl` | `ExchangeOrderMapper` | 校验 A 是否为 `from_user_id`（否则 `1003`）；状态 `3`→`2102`、`5`→`2104` | 只读 |
| 25 | 同上 | — | 常量时间比较 `verifyCode` 与库中值，不等抛 `2103` | — |
| 26 | 同上 | `ExchangeOrderMapper.verify` | `UPDATE exchange_order SET order_status=3, finish_time=NOW() WHERE id=? AND order_status=2` | 事务内 |
| 27 | 同上，影响行数=0 | — | 抛 `2102`（并发重复核销）；后续加分代码不会执行 | 回滚 |
| 28 | 同上 | `ItemMapper` | I₁ 由 `2` 置 `3` 已完成；I₂ 同样置 `3` | 事务内 |
| 29 | 同上 | `CreditService`（模块 07） | A、B 各 `+5`（`reason_type=finish`，`ref_id=orderId`）：写 `credit_log` + 原子更新 `user.credit_score` | 同事务 |
| 30 | 事务提交 | — | 核销完成 | 提交点 |
| 31 | `AppointmentServiceImpl` | `NotifyService` + 模块 07 评价提醒 | `AFTER_COMMIT` 通知双方“已核销，7 天内可互评” | 事务外 |

关键点：第 26 步的条件更新是唯一幂等闸口。两个核销请求并发时，数据库行锁保证只有一个能拿到影响行数 1，另一个在第 27 步被拦下，因此第 29 步的加分绝不会重复执行——这比“先查状态再决定是否加分”可靠得多。

### 6、阶段五：互评

| 步 | 发起方 | 接收方 | 动作 | 事务 |
| --- | --- | --- | --- | --- |
| 32 | A / B（`[UI-08]` 唤起弹窗） | `ReviewController`（模块 07） | `POST /api/reviews`：`orderId`、`score`、`content`、`tags` | — |
| 33 | 同上 | — | 校验：参与方、订单已完成、完成时间在 7 天内（超期 `2302`）、未评价过 | — |
| 34 | 同上 | `ReviewMapper` | 插入评价，触发 `uk_order_from` 唯一索引；冲突返回 `2301` | 事务内 |
| 35 | 同上 | `CreditService` | 收到好评方 `+3`（`good_review`） | 同事务 |

### 7、事务边界与幂等闸口汇总

| 阶段 | 事务范围 | 幂等手段 | 失败后果 |
| --- | --- | --- | --- |
| 发起锁单 | `exchange_order` 插入 + 两件 `item` 条件更新 | `WHERE status=1` 条件更新 + `uk_order_no` | 整体回滚，物品均回到在售 |
| 接单 | 单据状态 `0→1` | `WHERE order_status=0` | 回滚，仍为待确认 |
| 预约 | 单据 `1→2` + 写入 `verify_code` | `WHERE order_status=1` | 回滚，核销码作废不可用 |
| 核销 | 单据 `2→3` + 两件物品置完成 + 双方加分 | `WHERE order_status=2` | 整体回滚，不产生“核销了没加分” |
| 取消 | 单据 →`4` + 成对解锁 | `WHERE order_status IN (0,1,2)` | 回滚，单据状态不变 |
| 互评 | 评价插入 + 加分 | `uk_order_from` 唯一索引 | 冲突返回 `2301`，无副作用 |

### 8、超时与异常分支

| 场景 | 触发条件 | 系统动作 | 用户可见结果 |
| --- | --- | --- | --- |
| 抢单失败 | 他人已锁 I₁ 或 I₂ | 事务回滚，返回 `2101` | “手慢了，该物品已被抢先锁定” |
| 超时未接单 | `0` 状态超 24 小时 | 置 `4`，成对解锁，原因“超时未接单” | 详情显示已取消，物品回到在售 |
| 超时未预约 | `1` 状态超 48 小时 | 置 `4`，成对解锁，原因“超时未预约” | 同上 |
| 面交未核销 | `2` 状态超预约时间 24 小时 | 置 `5` 违约，成对解锁，扣 A `-10` | 详情显示已违约，A 信用分下降 |
| 归责争议 | 实际为 B 爽约 | A 经模块 07 提交单次申诉（写 `report` 工单） | 管理员复核后回补或转扣 B |
| 核销码错误 | 扫码内容不匹配 | 返回 `2103`，单据状态不变 | “核销码无效，请重新扫码” |
| 重复核销 | A 重复提交或网络重试 | 条件更新影响行数 0，返回 `2102` | 提示已完成，不重复加分 |
| 超时后核销 | 单据已被判 `5` 违约 | 返回 `2104` | “该流转单已超时关闭，如有异议可提交申诉” |

## （二）捐赠到电子凭证与公开验真

本流程展示快捐从申请锁单、社团隔离审核、解耦生成电子凭证到鉴权流式下载与扫码脱敏验真的全链路。核心约束为“审核落库与 PDF 渲染事务解耦”以及“`certificate/` 目录绝不对外做静态映射”。

| 步骤 | 参与方 / 组件 | 动作与调用 | 数据与状态变化 | 事务与降级说明 |
| --- | --- | --- | --- | --- |
| 1 | 学生 → `DonationController` | 提交 `POST /api/donations`（`itemId, clubId, remark`） | 无 | `@Valid` 校验入参，拦截器校验会话与停用态 |
| 2 | `DonationServiceImpl` | 校验认证态与本人 `1` 在售物品；调 `ItemService.changeStatus(itemId, 1, 2)` | `item.status: 1 → 2`（锁定） | 事务 1 内；影响行数=0 抛 `2101` 回滚 |
| 3 | `DonationServiceImpl` | 写入 `donation` 申请记录 | `donation` 新增（`audit_status=0`） | 事务 1 内；与步骤 2 原子提交 |
| 4 | `NotifyService` | 发送待审核通知给目标社团 | `notify` 新增 1 条 | 事务 1 `AFTER_COMMIT`，失败仅记 `warn` |
| 5 | 公益社团 → `DonationController` | 提交 `POST /api/donations/{id}/audit`（`pass, auditRemark`） | 无 | 校验社团角色与 `club_id` 归属（越权 `1003`） |
| 6a | `DonationServiceImpl`（通过分支） | 生成 `certificate_no`；条件更新 `donation.audit_status: 0 → 1`；调 `ItemService.changeStatus(itemId, 2, 3)` 与 `CreditService.addScore(donorId, +5, "donation", donationId)` | `donation.audit_status=1`、`certificate_no` 落库；`item.status: 2 → 3`；捐赠人积分 `+5` 且 `credit_log` +1 | 事务 2 内；重复审核条件更新影响行数=0 抛 `2102` |

事务边界总结：步骤 2～3 为事务 1（申请锁单），步骤 6a 或 6b 为事务 2（审核落库与物品终态/解锁），步骤 7 的 PDF 渲染与步骤 4、8 的通知审计全部置于事务之外，通过下载接口的按需补偿渲染闭合故障恢复路径。

| 缓存键 | TTL | 为何是这个值 |

### 5、与模块 08 的关系

模块 09 只做“召回与排序”，不重复实现检索逻辑：召回阶段的在售过滤（`status=1 AND is_deleted=0`）复用模块 08 的固定条件口径，两者共用 `ItemMapper` 的查询片段。区别在于模块 08 面向“用户主动筛选”，必须支持任意组合条件与分页；模块 09 面向“系统主动推送”，只按分类与热度取固定 12 条，因此不复用 `PageHelper`，直接 `LIMIT` 取数。

## （二）关键安全机制落地细则

### 1、会话安全、CSRF 同源防护与停用实时失效

1、Tomcat 10 会话 Cookie 配置：在应用上下文（`META-INF/context.xml` 或 `web.xml`）显式开启 `useHttpOnly="true"`，配置 `Rfc6265CookieProcessor sameSiteCookies="lax"`，会话空闲超时设为 30 分钟；生产若启用 HTTPS 则开启 `secure="true"`。

2、防会话固定与同源校验：登录成功后在写入 `SESSION_LOGIN_USER` 前调用 `request.changeSessionId()` 强制更换 `JSESSIONID`；拦截器对所有非白名单 `POST` 写请求检查 `Origin`（缺失时回退检查 `Referer`），解析其 `scheme + host + port` 与当前请求服务器地址比对，不一致时立即拦截并返回 `1003`。

3、停用账号旧会话实时失效：后台管理员在模块 12 将用户置为 `status = 0` 时无需依赖全集群会话广播，而是由 `AuthInterceptor` 在每次受保护请求中经 `AuthService.getAuthState(userId)` 走主键索引执行毫秒级状态复核；一旦检测到 `status != 1`，立即销毁该旧 Session 并返回 `1005`，确保被封禁账号无法再执行任何发布、下单、核销、快捐、评价或申诉操作。

4、登录防爆破与降级：连续输错密码或角色不匹配达 5 次后，通过 `cl:auth:fail:{username}` 触发 5 分钟冷却；若 Redis 不可用，`RedisHelper` 捕获异常记 `warn` 后直接放行，确保缓存故障不阻断正常登录演示。

### 2、角色隔离核销与越权防护边界

1、核销双角色强制分离：模块 05 预约接口（`#16`）仅生成并持久化绑定该 `order_id` 的一次性 `verify_code`（经 `SecureRandom` 生成 8 位大写字母数字码），响应体严禁回传 `verify_code`；物品所有者（`to_user_id`）仅可调用 `#18 GET /api/orders/{id}/qrcode` 获取二维码，发起方（`from_user_id`）无权调用 `#18`；当面验货后仅发起方（`from_user_id`）可调用 `#17 POST /api/orders/{id}/verify` 提交核销，物品所有者调用 `#17` 一律拦截返回 `1003`。

2、垂直与水平越权双重校验：垂直越权由 `PermissionUtil.checkRole` 拦截（学生账号访问 `/api/admin/**` 或社团审核接口直接返 `1003`）；水平越权由 `checkOwner`、`checkOrderParticipant`、`checkClubAccess` 在 Service 层逐笔校验数据库记录归属，严禁信任前端传入的 `userId`、`ownerId` 或 `clubId`。

3、公益社团数据隔离：社团账号查询捐赠列表（`#20`）、执行审核（`#21`）或下载凭证（`#22`）时，后端强制从 Session `LoginUser` 获取该社团账号对应的 `club_id` 并作为 SQL 必选条件注入，跨社团访问直接返回 `1003`。

### 3、文件上传防恶意执行与凭证目录隔离

1、`upload/` 实拍图防护：目录置于 Tomcat 应用部署目录之外并关闭脚本执行权限；上传严格按“大小 ≤ 2MB → 扩展名白名单 → 文件头魔数校验（JPEG `FF D8 FF`、PNG `89 50 4E 47`、WebP `RIFF....WEBP`）→ `ImageIO` 解码重编码压缩”四步处理，重命名采用随机 UUID，彻底剥离图片隐写脚本与 EXIF 隐私信息。

2、`certificate/` 非静态隔离与防路径遍历：Tomcat 严禁为 `certificate/` 配置任何静态资源映射，直接请求 `/certificate/...` 无法访问任何文件；完整 PDF 仅通过 `#22 GET /api/donations/{id}/certificate` 校验“当前用户为捐赠人 `donor_id` 或接收社团 `club_id`”后流式输出；`FileStorageService` 强制校验 `certNo` 匹配 `^CLD(\d{6})\d+$`，拼装路径后执行 `targetPath.toAbsolutePath().normalize().startsWith(baseDir)` 防御 `../` 路径遍历。

3、公开验真最小字段脱敏：捐赠凭证上的二维码指向公开验真接口 `#23 GET /api/donations/verify?certificateNo=...`，仅返回 `certificateNo`、`itemTitle`、`clubName`、`donorMasked`（如“林**”）、`auditTime` 与 `valid` 六个最小非敏字段，不返回学号、联系方式、真实全名或本地文件路径。

### 4、注入防护、输出转义与敏感数据脱敏

1、SQL 注入防护：所有 MyBatis Mapper XML 参数一律使用 `#{}` 预编译占位；动态排序（如模块 08 物品检索 `sort` 参数）仅允许前端传入枚举代号（`latest` / `hot` / `price_asc` / `price_desc`），由服务端 `Map<String, String>` 白名单映射为固定 `ORDER BY` 片段，严禁使用 `${}` 拼接用户输入。

2、XSS 防护：物品标题、描述、留言、评价内容与举报说明均为纯文本存储（不开放任意 HTML 富文本标签），JSP 页面统一使用 JSTL `<c:out value="${...}" escapeXml="true"/>` 或 `fn:escapeXml` 输出，前端异步渲染使用 `textContent` 而非 `innerHTML`。

3、日志与异常脱敏：`@OperLog` 切面（模块 14）在序列化请求参数前通过脱敏器剔除 `password`、`oldPassword`、`newPassword`、`confirmPassword`、`verifyCode` 等敏感键，对 `studentNo` 保留前 4 后 2 位（中间以 `*` 替代）；`GlobalExceptionHandler` 对未捕获异常仅在服务端 `error` 日志保留堆栈，响应体固定返回 `code=5001` 与通用中文提示。

## （二）目录规划与静态资源映射

1、`upload/` 静态只读映射

在 `spring-mvc.xml` 中把 URL 路径映射到容器外目录，避免图片打进 WAR（重新部署即丢失）：

```xml
<!-- spring-mvc.xml：静态资源与视图 -->
<mvc:resources mapping="/upload/**" location="file:/data/campus-loop/upload/" />
<mvc:resources mapping="/static/**" location="/static/" />

<mvc:default-servlet-handler />
<mvc:annotation-driven />
```

要点：

1、`location` 使用 `file:` 前缀指向容器外绝对路径，WAR 重部署不影响已上传图片。

2、只映射 `/upload/**`，绝不映射 `/certificate/**`——后者一旦映射，任何人猜到文件名即可下载他人捐赠凭证。

3、Tomcat 侧需确认未启用 CGI：`conf/web.xml` 的 CGI Servlet 保持注释；`upload/` 目录禁止执行脚本（Linux 下挂载 `noexec` 或将目录属主设为 Tomcat 运行账号且不给组写权限）。

2、`certificate/` 非静态受保护目录

1、目录位于 `/data/campus-loop/certificate/`，不在 `webapps` 下，Tomcat 无从将其作为静态资源暴露。

2、唯一访问入口是 `GET /api/donations/{id}/certificate`：`DonationController` 校验当前用户为捐赠人（`donor_id`）或接收社团（`club_id`），通过后由 `FileStorageService.readCertificateStream(certNo, out)` 以 `application/pdf` 流式写出，禁止整文件读入内存（凭证可能含图片，单件可达数 MB）。

3、验真走公开接口 `GET /api/donations/verify?certificateNo=...`，只返回脱敏字段，不返回文件流。

3、映射自检方法

| 检查 | 命令 | 通过标准 |
| --- | --- | --- |
| 图片可访问 | `curl -I http://localhost:8080/campus-loop/upload/202611/test.jpg` | `200`，`Content-Type: image/jpeg` |
| 凭证不可静态访问 | `curl -I http://localhost:8080/campus-loop/certificate/202611/CLD001.pdf` | `404`（不是 `200`，出现 200 说明映射配错） |

```xml
</session-config>
```

时区统一：JDBC URL 的 `serverTimezone=Asia/Shanghai`、JVM 启动参数 `-Duser.timezone=Asia/Shanghai`、MySQL `time_zone='+08:00'` 三者必须一致。任一处不统一，`appoint_time` 的“超预约 24 小时判违约”就会出现整体偏移，这是超时任务最容易踩的坑。

| 2 | 数据库连通 | `mysql -ucampus_loop -p -e "use campus_loop; show tables;"` | 返回 15 张表 |

| 7 | 目录可写 | 上传一张物品图 | 落盘 `/data/campus-loop/upload/yyyyMM/`，DB 有 `item_image` 记录 |

## （五）SQL 快照与 WAR 包回滚（5 分钟）

课程演示要求“5 分钟内可回滚到上一可用版本”，因此发布前必须留三样东西：数据库快照、上一个 WAR、Git Tag。

1、发布前留档（约 2 分钟）

```bash
# ① 数据库快照：结构 + 数据全量，带时间戳
mysqldump -ucampus_loop -p \
  --single-transaction --routines --triggers \
  --default-character-set=utf8mb4 \
  campus_loop > /opt/tomcat/backup/campus_loop_$(date +%Y%m%d_%H%M).sql

# ② 当前 WAR 另存为上一个版本
cp /opt/tomcat/webapps/campus-loop.war \
   /opt/tomcat/backup/campus-loop_$(date +%Y%m%d_%H%M).war

# ③ 打 Git Tag，标记本次发布点
git tag -a "release-$(date +%Y%m%d-%H%M)" -m "设计阶段联调版本"
git push origin --tags
```

2、回滚步骤（约 3 分钟）

| 步 | 操作 | 命令 | 耗时 |
| --- | --- | --- | --- |
| 1 | 停应用 | `systemctl stop tomcat`（或 `shutdown.sh`） | 20s |
| 2 | 还原数据库 | `mysql -ucampus_loop -p campus_loop < /opt/tomcat/backup/campus_loop_20261121_1530.sql` | 60–90s |
| 3 | 换回 WAR | `cp /opt/tomcat/backup/campus-loop_20261121_1500.war /opt/tomcat/webapps/campus-loop.war` | 5s |
| 4 | 清理解压目录 | `rm -rf /opt/tomcat/webapps/campus-loop/` | 5s |
| 5 | 启应用 | `systemctl start tomcat`，`tail -f logs/catalina.out` 看到 `Server startup in xxx ms` | 30–60s |
| 6 | 冒烟验证 | 登录 + 打开首页推荐 + 查一条流转单详情 | 30s |

3、回滚的三条红线

1、只回滚代码、不回滚数据适用于“新代码有 bug 但数据未污染”；一旦新版本已写入错误数据（如状态机错乱），必须连同快照一起回滚，否则旧代码读到新数据会二次报错。

2、结构变更不可逆：若新版本执行了 `ALTER TABLE`（如加列），回滚 SQL 快照会丢失新列数据。因此设计阶段约定——联调期间禁止直接改线上表结构，DDL 变更必须走“先改 `schema.sql` + 重建 + 重新灌 `data.sql`”的路径，并在 Git Tag 中记录。

3、上传文件不回滚：`upload/` 与 `certificate/` 是增量数据，回滚数据库会使部分文件失去引用，但不得删除文件——孤儿文件由定时清理任务在 30 天后处理，人工删会误伤仍在引用的图片。

4、版本与镜像留存策略

| 留存对象 | 数量 | 位置 | 清理方式 |
| --- | --- | --- | --- |
| SQL 快照 | 最近 5 份 | `/opt/tomcat/backup/` | 超出按时间删除最旧 |
| WAR 包 | 最近 3 个版本 | 同上 | 同上 |
| Git Tag | 每个发布点 1 个 | 远端仓库 | 不删除（审计需要） |
