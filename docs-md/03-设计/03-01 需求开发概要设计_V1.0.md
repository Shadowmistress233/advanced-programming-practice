# 一、概述

## （一）编写目的

本文档在《01-01 项目立项书（V1.1）》定稿与课程需求基准确认之后编写，负责将“要做什么”转化为“怎么做”的总体技术方案，明确系统架构、15 个业务模块边界、页面形态与交互要点、50 个对外接口契约、15 张数据库表结构及本次建设的影响范围与回退方案。

依据“唯一真源”原则，本文档严格守住概要设计层次边界：本文档回答“有哪些模块、对外接口与表结构长什么样、页面包含哪些区域与交互”，不编写类图、方法签名、伪代码或完整建表 SQL 代码块；类与方法级实现由《需求详细设计文档（DDD）》承担，视觉规范与 1440×900 像素级稿件由《UI 设计稿》承担。三份设计文档相互引用，不复制粘贴。

# 二、总体设计

## （一）设计目标与约束

本平台面向高校校内闲置流转与公益互助场景，目标规模为千级注册用户、百级日活跃用户，属于典型轻量级校园 Web 应用。设计目标按优先级排序如下：

1、正确性优先：双模式流转、扫码核销、诚信积分、公益快捐四类涉及物品归属与信用约束的业务，必须保证状态机严密、并发不超占、取消与超时成对解锁。

2、可维护与职责清晰：采用经典 SSM 分层架构，模块边界与 5 人分工严格对应，任一成员均能在短期内读懂其他模块契约并完成联调。

3、可扩展：双模式流转、积分规则与站内消息均基于配置化与统一抽象设计，后续扩展新流转方式、新通知类型或接入学校统一身份认证时，不侵入既有业务核心逻辑。

4、可降级：Redis 缓存、iText PDF 生成、消息推送等非核心依赖故障时，系统自动降级并记录日志，确保主业务闭环可演示、可交付。

项目约束条件如下：

1、技术栈锁定：采用 Spring 6.2.11 + SpringMVC + MyBatis 3.5.19 + MySQL 5.7 + Redis 5.0，运行于 JDK 17 与 Tomcat 10.1.61，不引入 Spring Boot，不采用前后端分离框架。

2、表现层锁定：采用 JSP + Bootstrap 5 + Ajax + ECharts 服务端渲染形态，页面视觉规范遵循《需求设计交付任务书》1440×900 桌面端基准（内容区宽 1240px、6 类语义色）。

3、合规与安全约束：平台不设资金池、不介入线上资金支付、不提供快递物流、不直连学校真实内网生产库；用户密码一律采用 BCrypt 不可逆哈希存储，禁止明文入库；金额字段一律使用 Java `BigDecimal` 与 MySQL `decimal(10,2)`，禁止使用 `float` 或 `double`；主键与接口业务 ID 统一采用 MySQL `INT` 与 Java `Integer`。

4、身份核验边界：保留“学号 + 校园邮箱核验”的业务定位与扩展接口预留；受限于课程环境无法直连校内邮箱/教务生产系统，本期演示与验收统一使用预置模拟账号与脱敏数据。

## （二）系统架构

系统采用自上而下的五层架构，请求依次穿过表现层、控制层、业务层、数据访问层与存储层，禁止跨层调用，所有 SQL 访问收口于 MyBatis Mapper 层：

| 层次 | 核心职责 | 关键技术与约束 |
| --- | --- | --- |
| 表现层（View） | 页面模板渲染、表单校验、异步交互与图表展示 | JSP + Bootstrap 5 + Ajax + ECharts；全站统一顶部导航、每页 12 条分页、写操作二次确认与结果提示 |
| 控制层（Controller） | 接收请求、参数格式校验、角色权限校验与统一响应封装 | SpringMVC `@Controller` 与 `@RestController`；接口统一返回 `Result<T>`，页面跳转返回逻辑视图名 |
| 业务层（Service） | 核心业务规则、状态机流转、并发控制、事务边界与降级处理 | Spring `@Service`；多表写操作与成对锁定/解锁统一使用 `@Transactional` 控制原子性 |
| 数据访问层（Mapper） | 结构化持久化操作、动态组合查询与分页 | MyBatis Mapper 接口 + XML 映射；严禁在 Service 拼接 SQL，参数一律使用 `#{}` 占位 |
| 存储层（Storage） | 业务主数据持久化、轻量缓存与静态文件存储 | MySQL 5.7.17（主库 `campus_loop`）、Redis 5.0（标签权重/热门榜/名额/验证码）、本地文件目录（`upload/`、`certificate/`） |

横切能力通过拦截器、AOP 切面与全局异常处理器统一织入，避免污染业务代码：登录与角色拦截器负责会话与权限校验；`@OperLog` AOP 切面负责关键操作异步审计；`@ControllerAdvice` 统一异常处理器负责将参数异常、业务异常与系统异常转换为标准错误码响应。

## （三）模块划分与依赖关系

全系统共划分为 15 个业务模块，编号顺序与《01-01 项目立项书（V1.1）》及《01-04 团队分工表（V1.1）》保持完全一致。按架构层次与调用方向分为四层分组，严格遵守“仅允许上层单向依赖下层或横切底座，严禁循环依赖”原则：

1、基础与横切底座层：模块 1（用户登录与权限控制）、模块 2（闲置物品发布与管理）、模块 10（站内消息与通知，横切基础服务）、模块 14（操作日志审计，横切 AOP 基础服务）。该层不反向依赖任何交易、公益或运营模块。

2、核心交易层：模块 3（双模式流转）、模块 4（技能交换板块）、模块 5（预约面交与扫码核销）。组内保持单向依赖（模块 5 依赖模块 3）。

3、公益与信用层：模块 6（闲置快捐通道）、模块 7（诚信积分与履约评价）。为杜绝模块 5 与模块 7 之间出现循环依赖，明确约束：模块 7 仅读取模块 3 的已完成流转单与评价数据，绝不反向依赖模块 5；模块 5 在扫码核销完成或超时违约闭环时，单向调用模块 7 提供的积分变更能力（依赖链路为：模块 5 → 模块 7 → 模块 3 → 模块 2 → 模块 1，构成严格有向无环图）。

4、运营与展示层：模块 8（物品检索与筛选）、模块 9（智能标签推荐）、模块 11（统计分析与数据看板）、模块 12（后台审核与违规处置）、模块 13（个人中心与信用档案）、模块 15（换物集市与主题活动）。该层仅单向聚合或治理下层数据，不被下层任何模块依赖。

# 三、模块设计（含界面设计）

本章严格按照《01-01 项目立项书（V1.1）》的 1～15 号顺序，逐一给出全部 15 个模块的“模块职责—功能要点—界面设计表”。界面设计以“页面—区域与控件—关键交互”三要素描述，页面名称与交互语义直接对齐《需求设计交付任务书》第 20 页的 20 个核心页面清单（文中以 `[UI-01]` 至 `[UI-20]` 标注对应编号），作为《UI 设计稿》绘制与前端还原的唯一依据。

全站页面统一遵守以下公共交互约定：顶部固定导航含 5 个主入口及右上角信用分、消息红点与头像菜单；所有列表页默认每页展示 12 条并统一提供状态筛选与分页条；所有写操作统一执行“前端校验 + 二次确认弹窗 + 后端结果提示”；状态标签严格采用 6 类语义色（循环绿 `#0F8A6A` 表主流程/已通过，寄售蓝 `#3B82F6` 表低价寄售，公益紫 `#7C3AED` 表捐赠与公益，琥珀 `#F59E0B` 表待审核/进行中，危险红 `#EF4444` 表违约/驳回/删除，正文墨 `#111827` 表标题与正文）；空列表、加载中、失败重试与无权限四类异常态均须提供清晰反馈。

## （一）用户登录与权限控制（模块 1）

模块职责：为学生（`student`）、公益社团（`club`）、平台管理员（`admin`）三类角色提供统一登录认证、会话维持、基于角色与资源归属的访问控制及安全退出能力。

功能要点：1）三角色统一登录入口，后端校验账号存在性、账号状态及 BCrypt 哈希密码，校验成功后在 Session 中保存 `userId`、`username`、`role`、`campus`、`authStatus`，并按角色返回对应默认首页路径；2）身份状态机：`user.status` 取值为 `1`（正常）、`0`（停用，停用账号登录返回 `1005`）；`user.auth_status` 取值为 `0`（未认证，仅可浏览，发起发布/流转/捐赠返回 `1003`）、`1`（已认证，拥有完整学生权限）、`2`（认证驳回）；3）保留“学号 + 校园邮箱核验”的身份认证模型与 Redis 验证码键位，课程演示版本直接提供三类预置已认证模拟账号；4）未登录访问受保护页面重定向至登录页，Ajax 请求未登录统一返回错误码 `1002`，越权访问返回 `1003`；5）退出登录立即销毁服务端 Session。

## （二）闲置物品发布与管理（模块 2）

模块职责：承载闲置物品的全生命周期管理，包括多图发布、合规预检、信息编辑、上下架、逻辑删除及物品详情展示。

功能要点：1）支持 1～5 张实物图上传（单张 ≤ 2MB，仅允许 JPG/PNG/WebP），自动压缩并默认以首图作为封面（`sort_no=0`）；2）发布前执行四重校验：标题（4～40 字）与描述（≤ 500 字）敏感词过滤、图片数量与大小校验（超限返回 `2001`）、寄售模式价格须 > 0 且 ≤ 同类均价 3 倍（非法返回 `2002`）、诚信积分门槛与同时在售数量上限校验（在售达 10 件或受限等级返回 `2003` / `2016`）；3）物品状态机（`item.status`）：`0`（待审核）→ `1`（在售，审核通过）→ `2`（锁定，流转单或捐赠单占用）→ `3`（已完成，核销或捐赠入库）；`0`/`1` 可流转至 `4`（已下架，本人下架或管理员驳回/违规下架），`4` 编辑重提后回 `0`（待审核）；非法越级操作（如编辑已锁定物品、对非在售物品下单）统一返回 `2005`；4）删除一律采用逻辑删除（`is_deleted=1`），锁定中物品禁止删除（返回 `2005`），保障历史流转单与捐赠凭证可追溯。

## （三）双模式流转（模块 3）

模块职责：用统一的流转单模型同时承载“以物易物（`exchange`）”与“低价寄售（`consign`）”两种核心交易模式，保障高并发下的防重复抢单与异常路径的成对解锁。

功能要点：1）以物易物模式发起时须指定发起人名下 1 件在售物品作为 `offer_item_id`，下单事务内通过数据库条件更新（`status=1 -> 2`）同时锁定目标物品与换出物品，任一更新影响行数为 0 即回滚并返回 `2004`（物品已被抢先）；低价寄售模式锁定目标物品且 `offer_item_id` 为空，款项由双方线下面交结清，平台不设资金账户；2）流转单状态机（`exchange_order.order_status`）：`0`（待确认）→ `1`（已确认，物品所有者同意）→ `2`（待面交，完成面交时间与自提点预约）→ `3`（已完成，由模块 5 扫码核销驱动）；异常终态分支：`0`/`1`/`2` 在满足条件时可进入 `4`（已取消，须填原因），预约超时 24 小时未核销由定时任务置为 `5`（已违约）；任何逆向或跨态变更（如对已取消单确认）统一返回 `2005`；3）取消、超时关闭、违约三条结束路径均在同一事务内执行成对解锁，将双方物品状态从 `2` 恢复为 `1`（在售）；4）严禁向本人发布的物品发起流转（返回 `2005`）。

## （五）预约面交与扫码核销（模块 5）

模块职责：承接已确认流转单的线下履约交付，实现校内自提点时段预约、一次性核销二维码生成、当面扫码核销及超时自动关单。

功能要点：1）流转单处于 `1`（已确认）状态时，参与双方可在 09:00–21:00 按半小时粒度选择未来有效时段，并从后台维护的校内自提点列表（如图书馆南门、宿舍区服务点、教学楼大厅等）选择地点；预约提交后流转单状态流转为 `2`（待面交），生成绑定该流转单与参与双方的唯一一次性核销码 `verify_code`；2）面交现场一方出示核销二维码，另一方扫码或输入核销码调用核销接口，校验权限（必须为该单参与方）、状态（必须为 `2`）及核销码有效性（无效或已使用返回 `2011`，已超时关闭返回 `2012`），核销成功将流转单置为 `3`（已完成）、双方物品置为 `3`（已完成），并单向触发模块 7 履约加分与模块 10 评价提醒；3）定时任务每小时幂等扫描超过预约时间 24 小时仍处于 `2`（待面交）的流转单，自动关闭并置为 `5`（已违约），同步成对解锁物品并按规则记入违约扣分，重复扫描不重复扣分或发消息。

## （七）诚信积分与履约评价（模块 7）

功能要点：1）积分变动规则统一配置在数据字典中（默认初始分 100 分：发布通过 `+2`、完成流转 `+5`、获得好评 `+3`、爽约/超时违约 `-10`、举报核实 `-15`），所有变动通过数据库原子增减并同步写入 `credit_log` 流水；2）四档信用等级映射：`≥ 90` 优秀（绿）、`75～89` 良好（蓝）、`60～74` 一般（琥珀）、`< 60` 受限（红）；低于 60 分限制同时在售数量，低于 40 分暂停发布权限并进入 7 天观察期（触发限制返回 `2016`）；3）仅状态为 `3`（已完成）且完成时间在 7 天内的流转单允许参与双方各评价一次，依托唯一索引 `uk_order_from` 防止重复评价（重复返回 `2009`，超 7 天返回 `2010`）；同对用户 7 天内高频互评仅计首次积分以防刷分；4）被扣分用户对单条扣分流水拥有一次申诉机会，管理员复核结果全程留痕并发送站内通知。

# 四、接口设计

## （一）接口规范

| 规范项 | 统一约定 |
| --- | --- |
| 路径风格 | 类 RESTful 风格，所有数据接口统一以 `/api` 为前缀，路径全小写，按业务域分组 |
| 请求方法 | 查询类使用 `GET`，新增、状态变更与逻辑删除统一使用 `POST`（便于审计与表单/Ajax 统一兼容） |
| 数据格式 | `GET` 参数走 Query String；普通写操作走 `application/json`（UTF-8）；含文件上传接口走 `multipart/form-data` |
| 统一响应 | HTTP 状态码恒返回 `200`，响应体统一为 `Result<T>{code, msg, data}`，靠业务 `code` 区分成功与错误 |
| 分页协议 | 列表接口统一入参 `page`（默认 1）与 `pageSize`（默认 12，上限 50），出参 `PageInfo<T>{total, list, pages, page, pageSize}` |
| 身份鉴权 | 基于服务端 HttpSession（Cookie 传递 `JSESSIONID`）；未登录返回 `1002`，角色不符或越权操作他人物品/单据返回 `1003` |
| 类型与精度 | 所有主键与业务外键 ID 统一为 `Integer`（对应 MySQL `INT`）；金额统一为 `BigDecimal`（保留两位小数）；时间统一为 `yyyy-MM-dd HH:mm:ss`（`Asia/Shanghai`） |
| 幂等与防重 | 核心写接口由数据库唯一索引（`uk_order_no`、`uk_order_from`、`uk_activity_user`）与状态条件更新兜底，不信任前端防抖 |

## （二）统一响应与错误码

响应成功时固定返回 `code=0`、`msg="ok"`；失败按号段分类：`1xxx` 为参数与权限认证类错误，`2xxx` 为业务规则与状态机错误，`3xxx` 为系统与外部依赖错误。前端拦截器按错误码段分别渲染表单行内提示、业务弹窗提示或系统繁忙兜底提示。

| 错误码 | 含义 | 典型触发场景 |
| --- | --- | --- |
| 0 | 成功 | 请求处理成功 |
| 1001 | 参数错误 | 必填参数缺失、长度或格式非法、驳回理由为空 |
| 1002 | 未登录 | Session 不存在或已过期 |
| 1003 | 无权限 / 越权 | 角色不符、操作他人资源、非本社团捐赠单、未认证学生发布 |
| 1004 | 账号或密码错误 | 登录账号不存在或 BCrypt 密码校验不通过 |
| 1005 | 账号已停用 | 用户表 `status=0` |
| 2001 | 图片不合法或超限 | 图片数量不在 1～5 张范围、单张超过 2MB 或扩展名/MIME 非法 |
| 2002 | 价格不合法 | 寄售价格 ≤ 0 或超出同类均价 3 倍上限 |
| 2003 | 发布数量超限 | 同一账号同时在售物品已达上限（默认 10 件） |
| 2004 | 物品已被抢先 | 并发下单或捐赠时物品条件更新（`status=1->2`）影响行数为 0 |
| 2005 | 状态不允许 | 越级状态流转、重复审核、删除锁定物品、引用中分类删除、向自己下单 |
| 2006 | 技能数量超限 | 同类有效技能（我能提供 / 我需要）超过 3 条 |
| 2007 | 不能邀约自己 | 技能互换发起人与技能发布者为同一用户 |
| 2008 | 物品状态不允许捐赠 | 待捐物品非本人所有或非在售状态 |
| 2009 | 重复评价 | 触发评价表唯一索引 `uk_order_from` |
| 2010 | 超过评价期限 | 距离流转单完成时间已超过 7 天 |
| 2011 | 核销码无效或已使用 | 核销码不存在、与流转单不匹配或已完成核销 |
| 2012 | 订单已超时关闭 | 超过预约时间 24 小时，已被定时任务关闭为违约态 |
| 2013 | 原密码错误 | 修改密码时旧密码 BCrypt 校验失败 |
| 2014 | 活动名额已满 | Redis Lua 脚本或数据库行锁扣减剩余名额返回 0 |
| 2015 | 重复报名 | 触发活动报名表唯一索引 `uk_activity_user` |
| 2016 | 信用分受限 | 诚信积分低于 40 分观察期限制发布，或低于 60 分触达受限在售数 |
| 3001 | 系统异常 | 未捕获运行时异常，由全局异常处理器兜底返回 |
| 3002 | 依赖服务不可用 | Redis 连接异常或 PDF 生成失败且无法即时返回 |

# 五、数据库设计

## （一）设计原则

1、命名规范：数据库名固定为 `campus_loop`，表名与字段名全部采用小写下划线命名；Java 实体类属性采用小驼峰，在 MyBatis XML 中显式声明映射关系。

2、类型与精度统一：字符集统一 `utf8mb4`、存储引擎统一 `InnoDB`；所有表主键统一为自增 `int`（`PRIMARY KEY (id)`），与 Java `Integer` 一一对应；金额字段统一 `decimal(10,2)`；时间字段统一 `datetime` 并由数据库默认值维护。

3、状态与逻辑删除：所有状态字段统一采用 `tinyint`，并在字段注释中列全取值语义，严禁使用字符串存储状态；涉及历史业务追溯的主表（`item`、`activity`）采用逻辑删除字段 `is_deleted`（`0` 正常、`1` 已删除）。

4、索引与外键策略：普通索引统一 `idx_` 前缀、唯一索引统一 `uk_` 前缀；高频组合查询建立组合索引；外键约束仅保留于强从属关系，其余业务表通过应用层事务与逻辑外键关联，避免误级联删除破坏历史审计单据。

## （三）表间关系

`user` 为全局核心主表，`item`、`skill`、`exchange_order`、`donation`、`credit_log`、`review`、`notify`、`report`、`oper_log`、`activity`、`activity_join` 均通过用户 ID 字段关联至 `user.id`。`item` 与 `item_image` 为一对多强从属关系；`item` 通过 `category_id` 关联 `category`。`exchange_order` 同时关联目标物品（`item_id`）、换出物品（`offer_item_id`）及买卖/交换双方（`from_user_id`、`to_user_id`），是系统唯一多方关联单据表。`donation` 关联待捐物品、捐赠学生与公益社团三方。`credit_log` 与 `review` 通过 `ref_id`、`order_id` 回溯至具体业务单据；`activity_join` 通过 `activity_id` 与 `user_id` 关联主题活动与报名学生。

# 六、非功能性设计

## （一）性能指标与优化手段

在 10 万条物品模拟数据规模下，首页与多条件检索接口目标响应时间 ≤ 300ms，其余常规业务接口 ≤ 500ms，支持校园高峰时段 50 并发稳定访问。关键手段包括：列表查询禁止 `SELECT *`，仅返回卡片必需字段；检索查询命中组合索引并配合分页限制单页上限；首页推荐结果缓存 10 分钟；数据看板通过 `stat_daily` 按天预聚合；Excel 报表导出采用 Apache POI 流式写出避免内存溢出。

## （二）安全设计

| 安全风险 | 防护措施 |
| --- | --- |
| 密码泄露 | 用户密码一律使用 BCrypt 不可逆哈希存储与校验，响应体与日志严禁回传 `password` |
| SQL 注入 | MyBatis 全站统一使用 `#{}` 参数化查询，禁用 `${}`；排序字段采用服务端白名单映射 |
| 越权访问 | SpringMVC 拦截器统一校验登录态与角色；Service 层强制校验资源归属（本人/交易双方/本社团） |
| XSS 与 CSRF | JSP 输出统一使用 JSTL `<c:out>` 或等价 HTML 转义；富文本/描述字段过滤危险标签；写操作校验会话与同源来源 |
| 文件上传风险 | 严格校验文件扩展名与真实 MIME 白名单（JPG/PNG/WebP），限制单张 ≤ 2MB、最多 5 张，随机 UUID 重命名存储于外部目录并禁止脚本执行权限 |
| 核销与隐私保护 | 核销码绑定流转单号与参与人且一次性有效；测试与演示数据全部脱敏，操作日志对学号、敏感参数做脱敏存储；电子捐赠凭证标注课程演示记录属性 |

## （三）可用性与降级策略

系统对所有非核心依赖强制实施异常捕获与降级兜底，确保单点依赖异常不拖垮主流程：1）Redis 不可用时，首页推荐自动降级为数据库按校区热门查询，活动名额扣减自动降级为 MySQL 行锁条件更新；2）iText PDF 凭证生成异常时，捐赠审核通过状态照常落库，凭证界面展示“生成中/重试生成”入口，不阻塞社团审核；3）站内通知与操作日志异步写入失败时仅输出本地错误日志，绝不导致流转或审核主事务回滚；4）定时超时扫描任务采用状态条件更新，天然支持重入幂等。

## （四）兼容性与前端适配

浏览器兼容 Chrome、Edge 最新两个正式版本；桌面端页面按 1440×900 设计稿（内容区宽 1240px）还原，向下完整适配 1366×768 分辨率，无横向滚动条与布局错位；移动端浏览器保持基础可浏览与可提交。数据库特性严格限定在 MySQL 5.7.17 范围，不使用 MySQL 8.0 窗口函数或专属语法；Java 源码与配置统一兼容 Windows 10/11 与 macOS 双开发平台。

## （一）系统边界与口径差异显式说明

本系统为全新独立建设的校园课程实践项目，不修改任何现有业务系统，不接入学校教务、一卡通真实内网生产库，不接入第三方支付与物流系统。依据任务书“不一致处显式标注并说明原因，不悄悄改口径”原则，将本文档相对《项目开发文档说明书》及参考样稿的对齐差异集中声明如下：

| 差异项 | 《说明书》/ 参考样稿原口径 | 本文档最终锁定口径 | 调整原因 |
| --- | --- | --- | --- |
| 密码存储策略 | 课程版可用明文或 MD5 | 统一采用 BCrypt 不可逆哈希 | 对齐团队《01-01 项目立项书》第三章安全基线，且实现成本可控 |
| 15 个模块编号顺序 | 5 为快捐、6 为积分、7 为推荐、8 为检索、9 为面交 | 按《01-01》《01-04》锁定：5 面交、6 快捐、7 积分、8 检索、9 推荐 | 保持与已归档立项书和 5 人分工表 100% 一致 |

## （三）对数据的影响与回退方式

1、无存量数据迁移影响：本系统为全新建设，不涉及任何存量数据库表结构改造或迁移（判断依据：原有校园闲置流转均分散在非结构化 QQ 群与纸质台账中，不纳入自动迁移）。

2、初始化数据边界：初始化脚本仅写入三类模拟账号（`admin`、`club01`、`student01` 及脱敏演示账号，初始密码均以 BCrypt 密文存储）、6 个一级分类、2 个认证公益社团、4 个校内自提点及 5 条默认积分规则，支持通过 `INSERT ... ON DUPLICATE KEY UPDATE` 幂等重跑。

3、数据保留与回退：业务单据永久逻辑保留，审计日志保留 1 年，统计日表保留 180 天后归档；演示或测试污染数据后，直接重跑初始化快照 SQL 即可在 1 分钟内恢复至干净基线状态。
